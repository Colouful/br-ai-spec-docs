# 企业级真实需求开发技术文档 Skill 优化实现方案

> 适用对象：内部研发团队、AI Skill 平台、技术负责人、前后端开发、测试、架构评审人员  
> 适用场景：基于存量 Spring Boot + MySQL 项目的增量需求开发，生成可评审、可开发、可联调、可测试、可上线、可回滚的企业级技术实现文档。  
> 当前版本定位：从“后端技术文档生成器”升级为“企业级真实需求开发落地 Skill”。

---

## 1. 当前 Skill 评审结论

当前 Skill 已经具备较强的工程意识，尤其是以下能力已经非常有价值：

1. 以存量 Spring Boot + MySQL 项目为目标场景，而不是泛泛生成技术方案。
2. 明确强调最小侵入、兼容优先、复用优先、可灰度、可回滚。
3. 强制进行 PRD 深度分析。
4. 强制进行前端原型与页面交互分析。
5. 强制生成页面-接口映射表。
6. 强制进行接口数量核对，避免原型交互遗漏接口。
7. 提供前端代码深度分析步骤，要求分析 API 调用、请求封装、分页规范、上传下载、响应结构。
8. 新增强制章节完整性检查，明确 §6.3 模块与类设计、§6.4 数据库设计、§6.5 接口设计、§7 兼容性、§8 核心流程、§9 测试设计、§10 风险、§11 上线回滚、§12 验收标准不得省略。

因此，当前 Skill 的基础方向是正确的。

但是，如果它要真正服务企业级真实需求开发，还需要从“生成文档”升级为“约束研发过程”。现在它更像一份强约束模板，还没有完全覆盖真实开发中的输入标准、现状扫描、差异识别、质量评分、交付产物拆分、示例驱动、可执行检查清单。

## 2. 当前 Skill 的核心问题

### 2.1 输入资料标准不够工程化

当前 Skill 要求用户提供需求名称、所属系统、PRD、原型图、前端源码地址、部署地址、现有项目信息等。但企业内部真实使用时，不同人能提供的资料完整度不同。

如果不分级，AI 会出现两个问题：

1. 用户只给一句话需求，AI 却输出看似完整但大量假设的文档。
2. 用户提供完整项目资料，AI 却没有按照可开发级标准充分分析。

需要补充“资料完整度等级”。

---

### 2.2 缺少后端代码现状扫描

当前 Skill 对前端代码分析写得比较细，但后端代码分析不足。

企业级后端技术文档最容易失败的原因不是 DDL 或接口写得少，而是没有贴合已有项目结构。例如：

- 项目是否已经有类似模块？
- 是否已有统一返回结构？
- 是否已有统一异常码？
- 是否已有数据权限机制？
- 是否已有操作日志注解？
- 是否已有字典表？
- 是否已有导入导出能力？
- 是否已有分布式锁、幂等、任务调度、文件上传能力？

如果不扫描后端现状，AI 生成的方案容易脱离项目实际，变成“新建一套理想架构”。这违反了当前 Skill 中“禁止擅自重构现有系统”和“复用优先”的原则。

---

### 2.3 缺少“差异报告”机制

当前 Skill 已经有“原型 vs 前端代码差异报告”，这是对的，但还不够。

企业真实开发至少需要以下差异报告：

| 差异类型 | 说明 |
|---|---|
| PRD vs 原型差异 | PRD 有功能，原型没有入口；原型有按钮，PRD 没规则 |
| 原型 vs 前端代码差异 | 原型有交互，代码未实现；代码有接口，原型未体现 |
| 前端代码 vs 后端接口差异 | 前端已调用接口，但后端没有；参数结构不一致 |
| 技术方案 vs 存量系统差异 | 方案引入了项目没有的框架、中间件或规范 |
| 数据库设计 vs 现有表结构差异 | 新增字段与历史字段语义重复，索引设计冲突 |

没有差异报告，文档只能“描述方案”，不能“发现问题”。

---

### 2.4 缺少示例文件体系

当前 Skill 本身写得比较细，但缺少配套示例文件。

对于 AI Skill 来说，示例文件的价值非常大。它们不是可有可无，而是决定输出稳定性的关键资产。

需要补充：

1. 示例 PRD。
2. 示例原型说明。
3. 示例前端代码。
4. 示例后端项目结构。
5. 示例数据库现状。
6. 示例接口文档。
7. 示例最终输出文档。
8. 示例测试用例。
9. 示例上线回滚方案。

没有这些示例，Skill 在不同模型、不同上下文、不同人员使用时，输出质量会波动。

---

### 2.5 缺少质量评分机制

当前 Skill 有强制章节检查，但没有评分。

企业内部落地时，最好让每份生成文档都有一个分数，便于判断能不能进入评审、能不能进入开发。

建议增加：

| 分数区间 | 说明 | 处理方式 |
|---|---|---|
| 90-100 | 可进入开发 | 允许进入开发排期 |
| 80-89 | 可进入技术评审 | 评审后补充细节 |
| 70-79 | 仅可用于方案讨论 | 不能直接开发 |
| 60-69 | 信息缺失严重 | 必须补充资料 |
| 60 以下 | 不可用 | 重新收集需求 |

## 3. 升级后的 Skill 定位

### 3.1 当前定位

```text
Backend Tech Doc Generator
为存量 Spring Boot + MySQL 项目生成企业级后端技术实现文档
```

### 3.2 建议升级定位

```text
Enterprise Requirement Implementation Skill
企业级真实需求开发落地 Skill
```

### 3.3 中文定位

> 基于 PRD、原型、前端代码、后端代码、数据库现状和企业研发规范，生成可评审、可开发、可测试、可上线、可回滚的真实需求技术实施文档。

### 3.4 核心价值

不是单纯“写文档”，而是解决真实研发中的 6 个问题：

1. 需求理解不一致。
2. 原型交互遗漏接口。
3. 前后端字段不一致。
4. 技术方案脱离存量系统。
5. 测试用例覆盖不完整。
6. 上线回滚没有准备。

## 4. 我会先问你的战略问题

下面这些问题不是为了拖慢进度，而是为了把这个 Skill 的产品定位摸清楚。

### 4.1 关于使用对象

1. 这个 Skill 主要给谁用？后端、前端、测试、产品，还是 AI 平台里的所有研发角色？
2. 使用者是否具备技术背景？如果是产品也能触发，输出是否需要分“产品可读版”和“开发可执行版”？
3. 是你个人提效工具，还是团队级规范工具？
4. 最终是放在 skill-q-platform 里作为一个 Skill，还是作为独立仓库里的工程规范？

### 4.2 关于目标效果

1. 你最希望它解决的问题是“文档不完整”，还是“开发返工多”？
2. 当前团队最大的痛点是接口漏、字段错、权限漏、测试漏，还是上线风险不可控？
3. 你希望它输出“一份综合文档”，还是“一组研发交付物”？
4. 输出文档是给人看，还是给 Codex、Claude Code、Cursor 这类 Agent 执行？

### 4.3 关于工程边界

1. 当前后端项目是不是统一 Spring Boot + MyBatis/MyBatis-Plus + MySQL？
2. 是否存在多租户、数据权限、按钮权限、菜单权限？
3. 是否有统一异常码、统一返回结构、统一日志规范？
4. 是否有 Apifox、Swagger、Knife4j、YApi 或内部接口平台？
5. 是否有统一的发布系统、灰度系统、配置中心？

### 4.4 关于示例资产

1. 你能不能拿一个真实但脱敏的需求做示例？
2. 是否可以提供一个真实前端页面代码片段？
3. 是否可以提供一个真实 Controller、Service、Mapper、DTO、VO 的目录结构？
4. 是否可以提供历史技术设计文档作为风格标杆？
5. 是否需要我帮你设计一套“客户标签管理”的完整示例包？

## 6. 建议新增的执行流程

### Step 0：识别任务模式

```markdown
### Step 0：识别任务模式

根据用户输入资料完整度，自动判断当前任务模式：

| 模式 | 触发条件 | 输出目标 |
|---|---|---|
| 需求澄清模式 | 只有一句需求 | 输出问题清单和假设前提 |
| 方案评审模式 | 有 PRD 和原型 | 输出可评审技术方案 |
| 开发落地模式 | 有 PRD、原型、前端代码、后端结构 | 输出可开发文档 |
| 上线交付模式 | 已有技术方案和代码变更 | 输出测试、上线、回滚、验收清单 |

如果资料不足，不允许伪装成完整开发文档，必须在文档中标注当前资料等级与风险。
```

---

### Step 3.6：后端代码现状分析

```markdown
### Step 3.6：后端代码现状分析

当用户提供后端源码路径或项目结构时，必须执行后端代码现状分析。

#### 3.6.1 项目结构识别

需要识别：

- 是否为单体项目或多模块项目
- 构建工具：Maven / Gradle
- 持久层：MyBatis / MyBatis-Plus / JPA
- 接口层：Controller 命名规范
- 业务层：Service / ServiceImpl 规范
- 数据层：Mapper / Repository 规范
- 对象模型：Entity / DTO / VO / Query / Converter 规范
- 公共能力：统一返回、统一异常、统一分页、统一权限、统一日志

#### 3.6.2 复用能力扫描

| 能力 | 是否存在 | 位置 | 本需求是否复用 | 说明 |
|---|---|---|---|---|
| 统一返回结构 | 待扫描 | 待填写 | 是 | 禁止新定义返回格式 |
| 统一异常处理 | 待扫描 | 待填写 | 是 | 复用全局异常处理 |
| 操作日志 | 待扫描 | 待填写 | 是/否 | 涉及新增、编辑、删除时优先复用 |
| 权限注解 | 待扫描 | 待填写 | 是 | 接口必须接入权限体系 |
| 数据权限 | 待扫描 | 待填写 | 视需求 | 涉及部门/用户范围时必须分析 |
| 字典能力 | 待扫描 | 待填写 | 是 | 枚举值优先复用字典表 |
| 文件上传 | 待扫描 | 待填写 | 视需求 | 上传/导入需求必须复用 |
| 导出能力 | 待扫描 | 待填写 | 视需求 | 导出需求必须复用 |

#### 3.6.3 类设计约束

新增类必须符合存量项目命名和分层规范，禁止凭空引入全新架构风格。

输出内容必须包含：

- 包结构树
- 新增类清单
- 修改类清单
- 复用类清单
- 调用链说明
- 类与接口映射
- 类与数据库表映射
```

### Step 3.7：数据库现状分析

```markdown
### Step 3.7：数据库现状分析

当用户提供现有表结构或数据库说明时，必须进行数据库现状分析。

#### 分析内容

| 分析项 | 说明 |
|---|---|
| 现有表复用 | 是否已有类似业务表 |
| 字段复用 | 是否已有同语义字段 |
| 枚举复用 | 是否已有字典表或枚举表 |
| 索引复用 | 是否已有可用索引 |
| 历史数据影响 | 新字段是否影响历史数据 |
| 大表风险 | ALTER 是否可能锁表 |
| 数据迁移 | 是否需要初始化或补偿数据 |
| 回滚脚本 | 是否能安全回滚 |

#### 输出要求

必须输出：

- 表变更总览
- 新增表 DDL
- 修改表 ALTER SQL
- 字段说明表
- 索引说明表
- 数据迁移脚本
- 回滚脚本
- 大表变更风险说明
```

## 8. 示例文件是否必须需要

结论：必须需要。

原因如下：

1. 示例文件是 Skill 的“行为标杆”。
2. 示例文件能减少 AI 输出漂移。
3. 示例文件能让团队成员快速理解如何使用。
4. 示例文件能给 Codex、Claude Code、Cursor 等 Agent 提供可执行上下文。
5. 示例文件能支撑评审和培训。

建议至少补充 9 类示例。

  },
