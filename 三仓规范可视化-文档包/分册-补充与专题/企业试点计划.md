# Enterprise Pilot Plan

> 文档状态：V1 可执行版  
> 适用范围：企业内部试点  
> 核心目标：选择一个真实项目，验证 `skill-q-platform` + `br-ai-spec` + `br-ai-spec-visual` 三仓闭环是否能提升 AI 研发规范化、复用率和交付可追踪性。

---

## 1. 试点目标

本次试点不追求一次性做成完整平台，而是验证一条最小但完整的业务闭环：

```text
Hub 创建 React 标准研发方案包
  ↓
br-ai-spec CLI 安装到业务项目
  ↓
开发者用 /spec-start 执行一个真实需求
  ↓
Visual 采集项目运行态
  ↓
Hub 看到安装与运行效果
```

试点成功的判断标准：

1. 开发者能在 10 分钟内完成项目接入。
2. 同一个 Manifest 能被至少 2 个项目复用。
3. 一次需求交付过程能留下完整 `.ai-spec` 和 OpenSpec 产物。
4. Visual 能看到项目资产和运行状态。
5. Hub 能看到安装记录和基础运行效果。

---

## 2. 试点项目选择

建议选择以下类型项目：

| 项目类型 | 推荐程度 | 原因 |
|---|---|---|
| React 中后台项目 | 高 | 与 `br-ai-spec` 当前前端主场景匹配 |
| Vue3 + Vite 组件库项目 | 高 | 适合验证规则、组件规范、文档生成 |
| 埋点系统前端平台 | 高 | 业务价值明确，可结合事件字典、查询分析 Skill |
| 核心交易 / 金融风控系统 | 低 | 试点阶段风险过高 |
| 老旧高耦合项目 | 中 | 可用于 audit-only，但不适合作为第一试点 |

第一试点建议：

```text
选择一个 React / Vue3 的内部中后台项目，功能复杂度中等，团队熟悉，风险可控。
```

| 角色 | 人数 | 职责 |
|---|---|---|

## 4. 试点范围

### 4.1 V1 做什么

```text
1. 创建一个 React 标准研发方案包。
2. 支持 CLI 从 Hub 安装方案包。
3. 生成 hub-lock.json。
4. 使用 /spec-start 跑一个真实需求。
5. Visual 展示项目 Manifest 和资产清单。
6. Hub 记录安装结果。
```

### 4.2 V1 不做什么

```text
1. 不做复杂推荐系统。
2. 不做跨团队权限矩阵。
3. 不做所有 IDE 全量适配。
4. 不做自动代码合并。
5. 不强制 CI/CD 门禁。
6. 不把 Visual 做成完整项目管理系统。
```

## 6. 试点实施步骤

### 阶段 1：准备

时间：1-2 天

任务：

1. 确认试点项目。
2. 确认 Hub 地址和数据库。
3. 确认 `br-ai-spec` CLI 可本地运行。
4. 确认 Visual 可本地或测试环境启动。
5. 确认试点需求。

输出物：

```text
试点项目清单
试点需求说明
试点 Manifest 初版
```

---

### 阶段 2：Hub 配置

时间：2-3 天

任务：

1. 在 `skill-q-platform` 新建资产。
2. 完成 Skill / Rule 审计。
3. 创建 Manifest。
4. 发布 `react-standard-delivery@1.0.0`。
5. 验证 Export API。

输出物：

```text
已发布 Manifest
资产审计记录
Manifest Export JSON
```

---

### 阶段 3：CLI 接入

时间：2-3 天

任务：

1. 在业务项目执行 `hub install`。
2. 检查 `.agents/registry/hub-lock.json`。
3. 检查 `.agents/rules` 和 `.agents/skills`。
4. 检查 IDE 命令入口。
5. 执行 `hub diff` 验证一致性。

输出物：

```text
业务项目接入记录
hub-lock.json
CLI 安装日志
```

---

### 阶段 4：真实需求执行

时间：3-5 天

任务：

1. 开发者使用 `/spec-start` 开始需求。
2. 按流程产出 PRD / 设计 / 任务 / 测试 / 归档。
3. 记录 AI 返工次数。
4. 记录门禁阻断点。
5. 记录最终交付耗时。

输出物：

```text
.ai-spec/history/<run-id>/
openspec/changes/<change-id>/
需求交付记录
问题记录
```

---

### 阶段 5：Visual 接入

时间：1-2 天

任务：

1. 在 Visual 创建 Workspace。
2. 配置 Collector。
3. 上报项目资产和运行态。
4. 检查项目资产画像页。
5. 检查 Runs / Changes 展示。

输出物：

```text
Visual 工作区
项目资产画像
运行记录看板
```

---

### 阶段 6：复盘

时间：1 天

任务：

1. 收集团队反馈。
2. 统计关键指标。
3. 输出问题清单。
4. 确认下一轮迭代。

输出物：

```text
试点复盘报告
问题修复计划
V2 范围建议
```

## 7. 关键指标

### 7.1 接入指标

| 指标 | 目标 |
|---|---|
| 首次接入耗时 | ≤ 10 分钟 |
| CLI 安装成功率 | ≥ 90% |
| Manifest 安装成功项目数 | ≥ 2 |
| 安装后 diff 异常数 | ≤ 3 |

### 7.2 交付指标

| 指标 | 目标 |
|---|---|
| 需求流程完整率 | ≥ 80% |
| 产物归档完整率 | ≥ 80% |
| AI 返工次数 | 有记录即可，V1 不强控 |
| 门禁阻断可解释率 | ≥ 90% |

### 7.3 复用指标

| 指标 | 目标 |
|---|---|
| 同一 Rule 被多个项目复用 | ≥ 2 个项目 |
| 同一 Skill 被多个 run 使用 | ≥ 3 次 |
| Manifest 被重复安装 | ≥ 2 次 |

---

## 8. 风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| CLI 安装破坏本地配置 | 覆盖已有 `.cursor` 或 `.agents` | 默认 dry-run + diff + 备份 |
| Manifest 太复杂 | 开发者看不懂 | V1 只做标准包，不做太多选项 |
| Visual 数据不准 | Collector 扫描不全 | 先只扫 `hub-lock.json` 和 `.ai-spec/history` |
| 团队不愿用 | 觉得流程重 | 提供 light / standard 两种模式 |
| AI 输出质量不稳定 | 返工多 | 强化 Rule 和测试 Skill |

## 9. 验收清单

```text
[ ] Hub 中存在已发布 Manifest
[ ] CLI 能搜索到该 Manifest
[ ] CLI 能安装该 Manifest
[ ] 本地存在 hub-lock.json
[ ] 本地存在 Skill / Rule 文件
[ ] /spec-start 可以正常启动
[ ] 产生 .ai-spec/history 记录
[ ] Visual 可以采集项目状态
[ ] Visual 可以展示项目 Manifest
[ ] Hub 可以看到安装记录
[ ] 完成试点复盘报告
```

---

## 10. 试点结束后的决策

根据结果选择下一步：

| 结果 | 决策 |
|---|---|
| 接入顺利，开发者认可 | 扩展到 3-5 个项目 |
| 接入困难但价值明确 | 优先优化 CLI 和文档 |
| Visual 价值明显 | 加强运行态和治理看板 |
| Hub 使用频率高 | 优先做 Manifest 配置器 |
| 团队不愿使用 | 回退到 audit-only 轻量模式 |
