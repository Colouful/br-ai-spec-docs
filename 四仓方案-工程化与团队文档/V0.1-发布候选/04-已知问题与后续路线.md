## 2. 文档治理原则

1. 不删除旧文档，先标记历史版本。
2. V0.1 发布候选文档作为当前实现依据。
3. 旧文档如与当前实现冲突，必须在入口处说明以 V0.1 为准。
4. 后续清理时优先处理“只扫业务项目展示 Manifest(清单)”这类已过期说法。

## 3. V0.2 建议

V0.2 建议只处理 V0.1 试点后暴露出的基础工程化问题，避免继续扩展大功能。

建议优先级：

| 优先级 | 建议 | 说明 |
| --- | --- | --- |
| P0 | Collector(采集器) 持久化 | 将 `br-ai-spec-visual` Collector Store(采集存储) 从内存迁到数据库或稳定存储。 |
| P0 | Asset Feedback(资产反馈) 持久化 | 将 `skill-q-platform` AssetUsageFeedback(资产使用反馈) 从内存存储迁到持久化模型。 |
| P1 | GitHub Actions CI(持续集成) | 对三仓关键测试、类型检查和构建建立自动验证。 |
| P1 | 一键本地联调脚本 | 降低四仓试点启动成本，但不能绕过真实命令和真实状态检查。 |
| P1 | 演示 Demo(演示项目) | 提供最小业务项目样例，用于复现 asset search(资产搜索)、asset install(资产安装)、上报和反馈闭环。 |
| P2 | 团队试点接入 | 选择一个真实业务项目验证最小链路，并收集资产质量和团队使用反馈。 |

## 4. 暂不建议做的事项

1. 不建议在 V0.1 后立刻追加大规模产品功能。
2. 不建议把内存反馈统计包装成长期生产指标。
3. 不建议继续让旧 Manifest(清单) 文档作为新成员入口。
4. 不建议在没有真实业务项目试点前打正式稳定版 tag(版本标签)。

## 5. 下一步顺序

1. V0.1 发布候选文档验收。
2. 三个代码仓库确认无未提交改动。
3. 三个代码仓库打 `v0.1.0-rc.1` tag(版本标签)。
4. 选择一个真实业务项目做试点。
5. 只跑最小闭环。
6. 收集反馈后再确认 V0.2 范围。
