# 阶段依赖关系说明

## 1. 各阶段之间的依赖关系

| 阶段 | 依赖阶段 | 是否可并行 | 说明 |
|---|---|---:|---|
| 00 项目理解与基线确认 | 无 | 否 | 必须先确认基线，不做代码重构 |
| 01 核心架构骨架调整 | 00 | 否 | 建立模块边界，不能跳过 |
| 02 核心业务链路迁移 | 01 | 否 | 依赖基础分层和本地运行时 |
| 03 权限门禁与治理能力 | 02 | 否 | 依赖核心链路可执行 |
| 04 可靠性与可观测性 | 02、03 | 否 | 需要在核心链路和 Guard 基础上补充 |
| 05 AI模型适配与扩展能力 | 01、02 | 部分可并行 | Model Adapter 可与 03 部分并行，但不能跳过 01 |
| 06 开发者体验与低入侵接入 | 02、04、05 | 部分可并行 | doctor/quickstart 依赖核心链路稳定 |
| 07 最终集成回归测试与验收 | 00-06 | 否 | 必须等待所有前置阶段完成 |

## 2. 哪些阶段可以并行

阶段 05 中的 Model Adapter 可以在阶段 03 开始后由另一执行模型并行处理，但必须满足：

1. 阶段 01 已通过。
2. 阶段 02 的 task-context 和 run.bundle 结构已稳定。
3. 不修改阶段 03 正在修改的 Guard 模块。
4. 合并前必须统一回归。

阶段 06 的部分文档和模板工作可以在阶段 04 后半段并行，但 doctor / quickstart 的代码实现必须等待阶段 04 验收通过。

## 3. 哪些阶段必须串行

以下阶段必须严格串行：

1. 阶段 00 → 阶段 01。
2. 阶段 01 → 阶段 02。
3. 阶段 02 → 阶段 03。
4. 阶段 03 → 阶段 04。
5. 阶段 06 → 阶段 07。

## 4. 每个阶段进入下一阶段的条件

每个阶段必须满足：

1. 当前阶段开发任务完成。
2. 当前阶段测试文档中的 P0 用例真实执行。
3. 当前阶段验收结果文档中所有 P0 项目通过。
4. 无阻塞级遗留问题。
5. 当前阶段变更已提交到独立分支或 commit。
6. 回滚路径已验证或明确记录。

## 5. 阶段失败时的处理方式

| 失败类型 | 处理方式 |
|---|---|
| 编译失败 | 停止进入下一阶段，修复后重新执行当前阶段测试 |
| 单元测试失败 | 不允许标记通过，必须修复或记录阻塞问题 |
| 集成测试失败 | 根据影响范围回滚当前阶段变更或修复 |
| Guard 误拦截 | 允许增加 allowlist，但必须记录审计和理由 |
| worktree 清理失败 | 执行 abort / clean / git worktree prune |
| 模型输出结构失败 | 最多重试一次，失败后转人工记录 |
| 需求不明确 | 标记【待确认】，不允许自行编造 |
