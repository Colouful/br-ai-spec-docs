# 02 核心业务链路迁移 - 技术实现文档

## 1. 阶段目标

迁移并打通 V0.1 主链路：init、plan、dry-run、run、verify、report。

## 2. 本阶段范围

- 实现 br-spec init
- 实现 Project Scanner
- 实现 OpenSpec Lite Builder
- 实现 openspec-view
- 实现 task-context/run.bundle
- 实现串行 Task Plan
- 实现单 worktree run
- 实现 verify/report 最小链路

## 3. 不在本阶段范围内的内容

- 不做复杂多 Agent
- 不做多 worktree 并行
- 不做完整 Hub/Visual
- 不做 RBAC
- 不自动处理 merge 冲突

## 4. 前置条件

1. 已阅读 `00-总览/00-AI执行总指令.md`。
2. 已确认前置阶段验收通过。
3. 当前 Git 工作区状态已记录。
4. 当前阶段分支已创建。
5. 如存在【待确认】项，必须先在验收结果文档中记录处理方式。


## 已知资料缺口与处理方式

| 缺失信息 | 影响范围 | 当前处理方式 |
|---|---|---|
| br-ai-spec 当前真实目录结构 | 影响具体文件定位 | 阶段 00 扫描确认，后续文档中使用【待确认】标记 |
| 当前包管理器 npm / pnpm / yarn | 影响测试命令 | 根据 lockfile 修正命令 |
| 当前测试框架 Vitest / Jest / 其他 | 影响测试文件位置 | 阶段 00 确认后更新 |
| 当前 CLI 入口文件 | 影响命令改造位置 | 扫描 package.json 的 bin/scripts |
| 当前模型调用实现 | 影响 Model Adapter 迁移方式 | 先新增适配层，不直接删除旧实现 |
| 当前 OpenSpec 目录是否已存在 | 影响迁移策略 | 支持 native/external/managed，默认 native |

原则：资料不足时继续生成可验证版本，但所有不确定点必须写入验收结果文档的“遗留问题”。不允许伪造测试结果，不允许伪造验收结果。

## 6. 当前问题

- 主链路之前过重且依赖过多平台能力
- AI 执行可能缺少清晰输入输出
- OpenSpec 直接全量读取会导致上下文过大
- run 过程缺少稳定状态文件

## 7. 目标设计

以本地串行链路为核心，不启用并行和平台依赖。每个命令输出明确文件，run 使用单 worktree 隔离。

## 8. 技术实现方案

### 8.1 模块设计

本阶段只实现本阶段范围内的模块。所有新增模块必须保持单一职责，禁止把跨阶段能力提前塞入当前阶段。

### 8.2 接口设计

1. 新增接口必须导出稳定类型。
2. 对外 CLI 行为必须保持中文输出。
3. 内部接口必须支持单元测试。
4. 如修改现有接口，必须提供兼容层或迁移说明。
5. 所有 JSON 文件必须带 `schemaVersion`。

### 8.3 数据结构

1. 阶段运行文件必须写入 `.ai-spec-local/` 或 `~/.br-spec/`。
2. 不确定字段必须使用【待确认】标记，不允许编造。
3. 运行态文件不默认入 Git。
4. 需要入库的规范文件必须由当前阶段明确说明。

### 8.4 配置设计

1. 默认 local-only。
2. 默认关闭 Hub、Visual、多 Agent、多 worktree 并行。
3. 高风险功能必须通过显式配置或命令参数开启。
4. 配置变更必须保留向后兼容。

### 8.5 调用流程

1. 执行前检查 Git 状态。
2. 执行中记录日志。
3. 执行失败写入错误信息。
4. 执行后生成当前阶段要求的输出物。
5. 如遇不可判断问题，写入验收结果文档，不允许静默忽略。

### 8.6 异常处理

1. 不能吞掉异常。
2. 所有错误必须输出中文说明。
3. 可恢复错误必须给出恢复命令。
4. 不可恢复错误必须写入验收结果文档。
5. 不允许为了继续执行而跳过失败检查。

### 8.7 兼容策略

1. 不删除旧入口。
2. 不破坏现有测试。
3. 新能力通过新增模块接入。
4. 必要时增加 adapter，避免直接重写旧逻辑。

### 8.8 回滚策略

1. 当前阶段所有改动应集中在阶段分支。
2. 如阶段失败，优先回滚当前阶段新增代码。
3. 不得回滚前置阶段已验收通过的能力。
4. 如生成运行态文件，使用 clean / abort 或手动删除当前阶段生成文件。

### 8.9 日志要求

1. 关键命令必须有日志。
2. Guard、Test、Evidence、Model 相关事件必须可追踪。
3. 日志不得包含密钥、Token、生产配置。
4. 日志必须能够支撑验收复盘。

### 8.10 权限要求

1. 不读取敏感文件。
2. 不修改生产配置。
3. 不执行破坏性 Git 操作，除非文档明确要求。
4. 高风险操作必须人工确认。

### 8.11 测试影响范围

## 10. AI 编程模型执行指令

你现在执行第 02 阶段：【核心业务链路迁移】。

请先阅读以下三个文档：

1. `02-核心业务链路迁移-技术实现文档.md`
2. `02-核心业务链路迁移-测试文档.md`
3. `02-核心业务链路迁移-验收结果文档.md`

你的任务是：

1. 理解本阶段目标和边界。
2. 只修改本阶段允许修改的文件和模块。
3. 按照技术实现文档完成开发。
4. 按照测试文档执行测试。
5. 将真实测试结果写入验收结果文档。
6. 判断是否满足进入下一阶段的条件。

严格禁止：

1. 扩大范围。
2. 跳过测试。
3. 删除测试。
4. 伪造结果。
5. 修改无关模块。
6. 引入未说明的大型依赖。
7. 破坏向后兼容。

完成后请输出：

1. 修改文件清单。
2. 实现摘要。
3. 执行的测试命令。
4. 测试结果。
5. 验收结果。
6. 遗留问题。
7. 是否建议进入下一阶段。

## 12. 风险与回滚方案

| 风险 | 影响 | 回滚方式 |
|---|---|---|
| 修改范围扩大 | 破坏前置阶段能力 | 回滚当前阶段分支改动 |
| 测试失败 | 阻塞进入下一阶段 | 修复失败项后重新执行测试 |
| 生成文件污染项目 | 影响低入侵要求 | 删除当前阶段生成文件并记录 |
| 配置不兼容 | CLI 无法执行 | 恢复默认配置并补兼容测试 |
| 不确定信息误判 | 后续实现偏差 | 使用【待确认】标记并暂停相关任务 |
