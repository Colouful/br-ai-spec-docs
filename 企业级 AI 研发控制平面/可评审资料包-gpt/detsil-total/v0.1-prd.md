# V0.1 产品需求说明书 PRD

文档状态：评审版  
目标版本：V0.1  
适用项目：br-ai-spec、skill-q-platform、br-ai-spec-visual  
目标样板：中台金融系统，技术栈为 Vue + Vite + Vuex、Spring Boot、MySQL、Redis、MQ。

---

## 1. 背景

当前 AI 编码工具已经能完成局部代码生成，但在企业级真实项目中仍有明显问题：

1. AI 容易乱改、漏改、过度实现，无法稳定遵守项目规范。
2. Cursor、Claude Code、Codex 等工具各自有规则、记忆、命令体系，企业难以统一治理。
3. AI 对项目长期决策、业务边界、接口契约、测试验收缺乏稳定记忆。
4. 复杂开发任务无法长时间稳定执行，长上下文越来越大后容易出现幻觉。
5. 多 Agent 并行如果没有隔离和合并机制，容易产生文件冲突、上下文漂移和责任不清。
6. 测试与验收证据缺失，导致 AI 生成结果难以进入正式研发流程。
7. Rule、Skill、Agent Profile、Hook、Test Gate 无法形成资产生命周期。

因此，需要构建一套企业级 AI 研发控制平面，将 AI IDE 纳入统一的规范、上下文、任务、验证、证据和观测体系。

---

## 2. 产品定位

一句话定义：

> 面向企业全栈项目的 AI 研发控制平面，通过规范资产、项目记忆、OpenSpec、Task DAG、多执行 Agent、Git worktree 隔离、Hook 门禁、Test Gate、Evidence 证据落盘和 Visual 观测，将 AI IDE 升级为可控、可验证、可审计的研发执行体系。

它不是：

- 不是单纯 Prompt 仓库。
- 不是单一 Cursor / Claude / Codex 配置工具。
- 不是普通多 Agent 聊天室。
- 不是自动替代研发流程的黑盒。
- 不是要求业务项目大规模改造的框架。

它是：

- 规范资产控制层。
- 本地项目执行控制层。
- 多 Agent 协同调度层。
- 测试验收与证据落盘层。
- 运行态可观测层。

---

## 3. 目标用户

### 3.1 研发个人

诉求：

- 在 Cursor / Claude / Codex 中更稳定地完成需求。
- 不需要每次重复解释项目规则。
- AI 改代码前能自动读取必要上下文。
- AI 产出测试、验收、交付报告。
- 失败后能有限自修复，而不是无限循环。

### 3.2 技术负责人

诉求：

- 统一团队 AI 开发标准。
- 知道 AI 做过什么、改了什么、为什么改。
- 可查看运行记录、测试证据、失败原因。
- 能沉淀最佳实践和失败经验。

### 3.3 测试与质量负责人

诉求：

- L2 / L3 需求必须生成测试计划、测试用例、验收清单。
- 测试失败不能直接标记完成。
- 失败修复过程有日志与证据。
- 最终交付报告可用于评审与归档。

### 3.4 架构与研发效能负责人

诉求：

- 将企业规范资产平台化管理。
- 支持多技术栈、多项目、多 IDE。
- 支持安全、审计、版本治理。
- 形成可量化的 AI 研发效能指标。

---

## 4. V0.1 核心目标

V0.1 聚焦一个最小但完整的企业级闭环：

```text
输入一个中台金融系统标准需求
→ 生成完整 OpenSpec
→ 构建 Context Pack
→ 渐进式加载规范资产
→ 拆分 Task DAG
→ 使用 Git worktree 隔离多执行 Agent
→ 合并 Patch Bundle
→ 执行 Hook 与 Test Gate
→ 最多 3 轮自修复
→ 生成验收证据
→ 上报 Visual
→ 形成最终交付报告
```

---

## 5. V0.1 范围

### 5.1 必须支持

| 编号 | 能力 | 说明 |
|---|---|---|
| P0-01 | 项目初始化 | 识别 Vue + Vite + Vuex、Spring Boot、MySQL、Redis、MQ |
| P0-02 | OpenSpec 支持 | L2 / L3 需求强制生成完整 OpenSpec |
| P0-03 | 渐进式资产加载 | Manifest → Summary → 命中详情 → 示例 |
| P0-04 | Context Pack | 生成 `run.bundle.json`，避免无限上下文膨胀 |
| P0-05 | Task DAG | 支持 dependsOn、writeSet、lockKeys、acceptanceRefs |
| P0-06 | Git worktree | 一个可执行 Task 一个 worktree，隔离执行 |
| P0-07 | Executor Pool | 支持多个执行 Agent 并行执行无冲突 Task |
| P0-08 | Hook 门禁 | Scope Guard、Dangerous File Guard、Test Gate、Evidence Gate |
| P0-09 | Test Gate | 执行 lint、单测、接口测试、集成测试等 |
| P0-10 | Evidence | 生成 `evidence-index.json`、测试报告、验收清单 |
| P0-11 | Resume | 支持长任务断点续跑 |
| P0-12 | Visual 上报 | 上报 Run、Task、Agent、测试、证据等核心事件 |

### 5.2 暂不支持

| 能力 | 暂缓原因 |
|---|---|
| 完整多租户权限 | V0.1 重点是本地控制与执行闭环 |
| 复杂资产市场 | 先沉淀企业内部规范包 |
| 全自动上线 | 高风险，后续接入 CI/CD 与审批 |
| 任意技术栈全覆盖 | V0.1 聚焦中台金融系统技术栈 |
| 完整商业化计费 | 不是当前阶段目标 |
| 自动修改生产数据库 | 禁止，V0.1 只生成迁移建议与脚本 |

## 6. 任务等级

### L1：轻量修复

示例：文案、样式、单文件 Bug。  
要求：轻量 Context，不强制完整 OpenSpec，不强制完整测试文档。

### L2：标准需求

示例：配置模块、普通 CRUD、新增页面、新增接口。  
要求：强制完整 OpenSpec，强制测试计划、测试用例、验收清单、证据落盘。

### L3：高风险需求

示例：金融流程、权限体系、资金相关、风控规则、数据迁移、MQ 消费、缓存一致性。  
要求：完整 OpenSpec、风险审查、人工确认 Gate、回滚方案、完整证据归档。

## 8. 主要风险与缓解

| 风险 | 说明 | 缓解 |
|---|---|---|
| 流程过重 | 小需求被复杂流程拖慢 | L1/L2/L3 分级 |
| 上下文过大 | OpenSpec 和规则过多导致幻觉 | 渐进式披露 + openspec-view + 压缩摘要 |
| worktree 管理复杂 | 多 worktree 清理和冲突处理成本 | worktree-index + 自动 clean/prune |
| 多 Agent 不可控 | 并行修改冲突 | Task DAG + writeSet + lockKeys + Merge Agent |
| 业务项目被污染 | 目录过多、侵入源码 | 只新增 openspec、.ai-spec、.ai-spec-local |
| 同事接受成本 | 需要理解新流程 | 提供样板链路和评审清单 |
