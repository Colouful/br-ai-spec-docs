# 一、评审结论摘要

**整体结论：有条件通过（Conditional Pass）。**

这套“企业级 AI 研发控制平面 V0.1”方案是一份极具工程务实精神的设计。它没有盲目追求“全自动 AI 编写全站”的幻觉，而是深刻理解了企业级（尤其是中台金融系统）研发的痛点，将 AI 的能力严格限制在“规范驱动（SDD）、沙盒执行、测试门禁和证据审计”的框架内。通过 `OpenSpec` 确立需求事实源，利用 `Git Worktree` 实现物理隔离，这是非常有前瞻性且极具实操价值的架构决策。

然而，该方案在追求“受控”的同时，陷入了**“本地过度工程化”**的陷阱。将 DAG 调度、多 Agent 并行控制、冲突解决、文件锁管理等重型编排逻辑全部塞入本地 CLI (`br-ai-spec`)，会带来极高的本地状态崩溃风险和极差的容错能力。同时，业务仓库的目录侵入性（即使自称最小化）在推广期仍会遇到不小的阻力。

建议在 V0.1 阶段大幅裁剪多 Agent 并行调度逻辑，优先打通“单 Agent 串行受控执行与证据闭环”，再逐步演进复杂编排。

---

# 二、关键优点

1. **务实的执行隔离机制 (Git Worktree)：** 这是本方案最大的亮点。放弃了让大模型在主工作区随意篡改的幻想，将每一个 Task 绑定到一个独立的 Git Worktree。这不仅解决了多文件并行的冲突问题，还天然提供了可回滚、可对比（Diff）的物理沙盒，极大地提升了安全性。
2. **坚持规范驱动开发 (OpenSpec / SDD)：** 强制 L2/L3 需求提供结构化的 `proposal, design, tasks`，并在 AI 执行中收敛上下文视图（OpenSpec View）。这从根本上治理了 AI 的“幻觉”和“过度实现”问题。
3. **闭环的测试与审计门禁 (Hook & Evidence)：** 没有证据就不能合并（Evidence Gate），测试不通过就触发自修复。这种将 CI/CD 理念前置到 AI IDE 运行时的设计，满足了企业级特别是金融级系统的合规要求。
4. **渐进式资产披露 (Progressive Disclosure)：** 避免了将企业级庞大的 Rule、Skill 和历史 Memory 一次性塞入 Prompt 导致上下文溢出或焦点模糊，设计了清晰的 L0-L4 加载层级。

---

# 三、关键问题

1. **本地控制器 (`br-ai-spec`) 职责过重，状态机极易崩溃：** CLI 在本地既要当调度器（Scheduler），又要当包管理器（Context Pack），还要管并发（Executor Pool）和 Git 分支（Worktree Manager）。本地开发机环境复杂，一旦 CLI 异常退出、断电或被强制 kill，本地遗留的僵尸 Worktree、未解除的 LockKeys 和破损的 `run.bundle.json` 将是一场灾难。
2. **“Merge Agent” 存在极高的代码污染风险：** 让大模型（Agent）去处理 Patch 合并和冲突解决（Merge Agent）是非常不可控的。代码合并应该是基于 AST 或严格 Git 算法的确定性行为，一旦 LLM 出现幻觉，可能会默默删除关键业务逻辑，且极难在后续排查。
3. **架构侵入性与业务心智负担依然较高：** 尽管声称“最小侵入”，但强制要求在业务根目录增加 `openspec/`、`.ai-spec/` 且需要入库，这要求业务团队完全改变现有的需求管理习惯（如从 Jira/Confluence 迁移到本地 Markdown）。
4. **V0.1 目标过于庞大：** 试图在第一版同时跑通 Graph DAG 拆解、多专家 Agent 并行、Git 隔离、自动测试与 Hub 同步。对于中台金融系统样板，这个链路太长，极易在早期测试中受挫。

# 四、分维度详细评审

### 1. 整体架构合理性
* **分析：** 三仓分离（Hub、Local、Visual）的顶层设计清晰。但层次划分在物理实现上出现了头重脚轻的问题。接入层（IDE）和执行/编排层（CLI）紧耦合在了开发者本地。
* **不合理之处：** 缺乏一个中心化的 Runtime（或 Gateway）。如果所有调度都在本地，团队成员之间无法共享执行状态，也无法利用云端的高性能沙盒环境。
* **建议：** CLI 应该退化为一个“富客户端”，只负责拉取指令、同步本地工作区和执行具体命令。复杂的 Task DAG 拆解和并行状态机应逐步上云或由轻量级确定性脚本管理。

### 2. 目标设计是否合理
* **分析：** 解决“受控”和“可审计”的目标非常精准，直击痛点。区分 L1/L2/L3 是成熟的工程思维。
* **风险：** V0.1 就要求多 Executor 并行执行，目标过大。
* **建议优先级：** 降低“多 Agent 并行 (DAG)”的优先级，优先打通“单线流转 + 测试门禁 + 证据落盘”的 MVP。

### 3. 面向未来 AI 大模型快速发展的适应性
* **评分：** 7/10
* **分析：** 方案对大模型能力的依赖被有效框定在 Task 级别，这是非常好的防御性设计。未来即便出现 GPT-5，本架构只需把 Task 粒度放大即可，不会轻易过时。
* **适配性风险：** 当前架构大量依赖特定的 JSON Schema 协议约束 AI 输出（如 `run.bundle.json`）。如果未来原生支持复杂 Tool Calling 或 MCP (Model Context Protocol) 成为绝对主流，这些自定义协议可能会成为技术债。
* **建议：** 拥抱标准协议。与 IDE 交互的数据结构应尽量向 MCP 靠拢，提升未来更换模型或 IDE 的平滑度。

### 4. 开发者上手难度
* **评分：** 4/10 （上手难度极高）
* **分析：** 开发者在原有的 `git pull/commit/push` 之外，必须学习一整套全新的生命周期命令（`br-spec plan/run/verify/resume`），并且要理解 Worktree 的概念。对于不熟悉底层 Git 机制的开发者，一旦陷入冲突，将不知所措。
* **优化建议：** 将命令无缝集成到 IDE 插件中，提供 GUI 可视化操作。绝不能让普通开发者手动去 `~/.br-spec/worktrees/` 目录下找代码修 Bug。

### 5. 对业务项目的入侵性
* **评分：** 5/10 （中度偏高）
* **分析：** `.ai-spec-local/` 不入 Git 是合理的。但 `openspec/` 强行植入业务代码库，意味着如果项目不用 AI 工具了，这些目录就成了历史包袱。
* **推荐低入侵方案：** 将 `openspec` 和资产配置中心化，或者支持通过配置文件指向外部仓库（类似 Git Submodule 或 Mono-repo 结构），实现物理代码与 AI 规则的解耦。

### 6. 系统可靠性与稳定性
* **评分：** 4/10 （生产级隐患大）
* **分析：** CLI 是个脆弱的单点。`dependsOn`、`writeSet`、`lockKeys` 如果计算有一丝偏差，就会引发 Worktree 代码覆写灾难。自修复逻辑（Repair Limit Guard）虽然有上限，但在本地循环执行仍然可能把 CPU 和网络打满。
* **建议：** V0.1 必须提供强力的 `br-spec abort & clean` 一键恢复能力，确保无论发生什么，开发者都能一键回到主干初始状态，清理所有幽灵进程和锁。

### 7. 安全性、权限与治理能力
* **评分：** 8/10
* **分析：** 设计了 Scope Guard, Dangerous File Guard, Secret Guard，并在 L3 强制人工审核，这在企业级产品中是非常出色的治理设计。
* **缺失项：** 脱敏机制。如果 AI 读取了带有真实用户数据的测试库配置或硬编码，上传给第三方大模型，存在合规风险。需要补充 Prompt 层的 PII（个人身份信息）拦截。

### 8. 可维护性与工程复杂度
* **分析：** `br-ai-spec` 作为一个 Node.js CLI，工程复杂度极高。它实质上在本地实现了一个小型的 Jenkins + 任务编排引擎。
* **技术债预警：** `scheduleExecutableTasks` 这个函数未来会演变成一个极其复杂的怪兽，处理各种边缘冲突。

### 9. 扩展性与复用性
* **分析：** Hub 的设计（Manifest, Rule, Skill）复用性极强，支持横向扩展。未来可以非常平滑地支持跨团队资产共享。

### 10. 成本与投入产出比
* **评估：** 初期研发成本很高（需要开发一套复杂的本地 CLI 和两个配套平台）。如果能切实降低金融系统的线上故障率，这笔投入是划算的。
* **风险：** 可能会遭到业务团队“因为太繁琐而不愿意用”的抵制，导致 ROI 归零。

# 七、是否建议通过

**结论：有条件通过**

**原因：** 架构的核心理念（SDD驱动、沙盒隔离、测试门禁）是完全正确的方向，具备极高的商业和工程价值。但不建议按目前的 V0.1 计划全盘启动开发。
**通过条件：** 必须砍掉 V0.1 中“多执行 Agent 并行并发（Task DAG）”和“LLM Merge Agent”这两个最高风险、最高复杂度的设计。回归到最稳妥的“单线串行生成 -> 隔离测试 -> 人工合并/机器确定性合并”的基线版本。

---

# 八、修改建议优先级

### P0 (阻断级，必须修改)
1. **废弃大模型驱动的 Merge Agent**。合并动作必须是确定性的脚本逻辑。发生冲突时立刻抛出给开发者，不盲目让 AI 自行裁决。
2. **将 Task DAG 退化为串行执行管线**。V0.1 不要挑战跨文件、跨上下文本地多进程并发修改。

### P1 (高优先级，严重影响推广)
1. **强化异常恢复体系**。CLI 必须提供绝对可靠的 `br-spec nuke` 或类似命令，能够在任何状态机异常崩溃后，一键清除 `.ai-spec-local` 缓存和外挂的 Worktree，恢复主工作区洁净。
2. **支持轻量级项目初始化**。允许 `.ai-spec` 和 `openspec` 放在全局用户目录 (`~/.br-spec/global-configs`) 或提供通过 Webhook 远程拉取配置的模式，降低对原项目的直接侵入。

### P2 (中优先级，架构演进)
1. 将与 IDE 交互的数据结构向 MCP (Model Context Protocol) 标准靠拢，方便未来快速接入更多官方支持的工具生态。
2. 在 Hook 中补充 PII（敏感数据）脱敏拦截机制。

# 九、推荐优化后的架构方向

建议将架构从“本地重调度”转向**“中心化调度与状态同步 + 本地轻量化执行 (Local-as-a-Runner)”**的方向：

1. **系统定位：** 依然是企业级研发控制平面，但 `br-ai-spec` 退化为一个智能的 Runner（类似 GitLab Runner），仅负责执行特定指令并上报结果。
2. **编排层上云：** Task DAG 规划、Context Pack 构建、冲突计算，放到 `skill-q-platform` 或本地开启的一个轻量级后台 Daemon 进程中计算，不要让每一次 CLI 唤起去承担高昂的计算开销。
3. **能力边界：** AI 只负责生成单个 Task 的 Patch Bundle。合并、应用 Patch 必须依靠传统的 Git Patch / Apply 工具。
4. **推荐的开发者使用路径：**
   - 开发者在系统新建需求（Web或IDE）。
   - 平台下发指令 -> 本地 Runner 自动拉起 Worktree。
   - 本地调用 IDE (Cursor/Claude) 注入上下文。
   - 开发者确认代码生成完毕，点击“验证”。
   - Runner 执行测试 -> 生成 Evidence -> 合并到功能分支 -> 清理现场。

# 十、分阶段落地路线

原有的 V0.1 目标过于庞杂，建议按照以下节奏重构你的 Roadmap：

## 阶段一：MVP 验证阶段（回归单兵作战底座）
* **目标：** 跑通“规范驱动 -> 隔离执行 -> 证据验收”的核心逻辑。
* **范围：** **仅单线程串行执行**。没有 Task DAG，只有线性的 Step。
* **必须建设能力：** `OpenSpec` 解析生成、单一 `Worktree` 隔离、Hook 门禁（Scope/Test Gate）、Evidence 基础落盘。
* **不建议建设能力：** 多 Agent 并发调度、LLM Merge、Visual 大屏展示（看本地 Markdown 报告即可）、Hub 资产中心（直接读本地 JSON 配置）。
* **验收标准：** 中台金融样板的 L2 需求，能够在一个 Worktree 内，被 AI 串行修改完成，通过 Lint 和单测，输出 Markdown 交付报告。

## 阶段二：平台化建设阶段（资产与观测）
* **目标：** 实现企业规则的可沉淀、可观测。
* **范围：** 上线 Hub 和 Visual 平台。
* **核心能力：** `skill-q-platform` 的 Manifest 与 Rule 分发，`br-ai-spec` 对接 Hub 同步资产。
* **治理能力：** L3 需求的人工审批流。
* **观测能力：** `br-ai-spec-visual` 接收本地 Runner 传回的 Event，形成企业级研发驾驶舱。

## 阶段三：企业级规模化阶段（复杂编排与团队协同）
* **目标：** 攻克大型需求的长上下文与并发效率瓶颈。
* **范围：** 引入 Task DAG 与 Executor Pool。
* **核心能力：** 智能拆解子任务，安全的多 Worktree 并行调度，确定性的 AST/Git 冲突合并机制。
* **扩展能力：** 支持跨团队复用 Skill，提供研发效能数据看板。

## 阶段四：AI 原生演进阶段（拥抱新一代范式）
* **目标：** 架构随大模型能力自动演化升级。
* **范围：** 探索新一代交互与执行范式。
* **方向：** 全面拥抱 MCP 协议；根据基座大模型（GPT-5 / Claude 3.5 Opus+）长窗口能力的增强，动态削弱人工 OpenSpec 的细粒度要求；引入自学习 Agent，自动根据历史失败的 Evidence 优化团队的 Rule 和 Skill 资产。

---

关于本地 CLI 承担过多调度逻辑导致的状态机崩溃风险，团队是否有备用的容灾（例如强制一键还原/清理幽灵状态）或简化降级方案？
