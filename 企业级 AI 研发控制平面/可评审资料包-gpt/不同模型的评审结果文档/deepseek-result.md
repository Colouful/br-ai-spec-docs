# 一、评审结论摘要

本方案是一份高度工程化、细节充分的企业级 AI 研发控制平面设计。它试图将 AI IDE 从“会写代码的助手”升级为受控、可审计、可并行协作的研发执行体系，整体思路清晰，核心机制设计（OpenSpec、Task DAG、Git Worktree 隔离、Evidence）具备很强的针对性和创新性。但方案目前存在 **过度设计、概念过载、对业务项目侵入性隐忧高、执行复杂度远超 V0.1 定位** 等问题，不适合直接作为 V0.1 落地。**我的结论是：有条件通过，但必须大幅削减 V0.1 范围，并重新审视 Agent、Worktree 等强约束对普通开发者的实际可行性。**

# 二、关键优点

1. **“Graph 管流程、Agent 管判断、Executor 管变更”的核心范式**：清晰区分了流程控制、专业分析和代码修改，避免了 AI 自由发挥导致的风险。
2. **OpenSpec 与渐进式披露机制**：将需求规格事实源化并压缩为视图，有效缓解上下文膨胀问题，是工程化的亮点。
3. **Git Worktree 隔离执行**：将任务并行与版本控制深度结合，为多 Agent 协同提供了可审计、可回滚的隔离环境，思路领先。
4. **Evidence 证据与审计链**：强制落盘测试结果、验收清单、修复记录等，真正让 AI 产出具备企业级可追溯性。
5. **三仓职责边界清晰**：br-ai-spec（本地控制器）、skill-q-platform（资产治理）、br-ai-spec-visual（观测）的拆分合理，耦合度低，便于分阶段建设。
6. **对金融级风险场景的敏锐感知**：L3 等级、Scope Guard、Dangerous File Guard、Repair Limit Guard 等设计体现了对安全与稳定性的重视。

# 三、关键问题

1. **V0.1 范围严重超载**：作为“最小可落地”，试图同时涵盖 OpenSpec、Task DAG、Worktree、多 Agent 并行、Hook、Test Gate、Evidence、Visual 等十余个重型机制，实际落地成本极高，预计远超 4-6 周。
2. **Agent 粒度与执行复杂度不匹配**：定义十余种 Agent，但大多数（如 Product Agent、Architect Agent）的输出仍依赖 LLM 或人工，实际执行中很难形成自动化闭环，可能会退化为“编写特定 Prompt 的脚本”。
3. **Git Worktree 强依赖引入较高接入门槛**：强制团队接受分支模型、worktree 外部目录、cherry-pick 合并策略，对不熟悉 Git 高级用法的团队是巨大障碍，且 Windows 环境下 worktree 支持存在较多坑点。
4. **业务项目侵入性评分被低估**：虽然声称只新增三个目录，但 `openspec/` 要求 L2 需求强制编写完整 proposal/design/tasks/spec delta，本质是引入了一种新的需求文档体系，对现有研发流程侵入性较高，可能遭到业务团队抵触。
5. **对 AI 模型能力过度悲观或过度前置**：方案设计了很多约束机制（如 Scope Guard、Repair Limit），似乎预设当前模型会频繁出错，导致系统高度复杂。随着模型能力快速提升，许多 Guard 可能在未来 6-12 个月内变成冗余，架构需预留简化空间。
6. **缺少对人类开发者工作流的尊重**：全流程由 CLI 和 Agent 主导，开发者似乎只负责发起命令和确认，这与现实中开发者需要随时介入、修改、调试的诉求矛盾，容易造成“平台推荐方案与开发者直觉冲突”。

# 四、分维度详细评审

## 一、整体架构合理性

**优点**：三仓架构清晰，模块职责分明；Graph-Governed Multi-Agent 思想先进；Task DAG + Worktree + Patch Bundle 构成完整的变更管理闭环。

**风险**：
- 过度抽象：Agent 分层多达 7 类，但分析型 Agent 缺乏明确的可替代执行体，V0.1 大概率会变成“几段 Prompt + 工程脚手架”。
- 调度与合并复杂度高：多 worktree 并行、lockKeys 冲突检测、语义化 cherry-pick，一旦出现冲突，依赖人工介入的概率极高，自动化程度受限。
- 架构中未体现本地 IDE 与远程模型调用的网络可靠性设计。

**不合理之处**：将“证据观测”作为独立平台 br-ai-spec-visual 在 V0.1 就要求接入，过于超前。V0.1 应优先保证本地单机闭环，Visual 可先用文件存储代替。

**优化建议**：V0.1 砍掉 Visual 远程上报，仅保留本地 evidence 输出；合并部分分析 Agent，简化为“Planner Agent”+“Executor Agent”；锁冲突检测可先采用保守串行化，逐步增强。

**推荐目标架构方向**：保持三仓，但 V0.1 重点打磨 br-ai-spec 单仓库本地能力，Hub 和 Visual 采用 mock 或文件模拟。

---

## 二、目标设计是否合理

**合理性判断**：目标明确（打穿中台金融系统一条 L2 需求），可验证（验收标准中包含 15 项硬性指标），但时间预算（4-6 周）与任务量严重不匹配，目标过大。

**目标优先级建议**：
- P0：OpenSpec 生成与校验、Context Pack、基本 Task DAG 与单任务 worktree 执行、核心 Hook（Scope + Dangerous File）、单元测试证据落盘。
- P1：多任务并行 worktree、Merge Agent、Repair Agent、Test Gate 多级门禁。
- P2：完整的 Visual 集成、多资产同步 Hub、resume 断点续跑。

**应保留目标**：打通全链路但允许部分环节暂为人工或半自动。

**需补充量化指标**：如“L2 需求从 OpenSpec 生成到测试通过的平均耗时”、“开发者额外投入时间（编写 OpenSpec 等）与 AI 产出代码质量提升比”。

---

## 三、面向未来 AI 大模型快速发展的适应性

**适配性评分**：7/10。

**优势**：OpenSpec 和资产清单可模型无关；Task DAG 定义了任务结构而非模型能力；渐进式披露不绑定特定 token 限制。

**风险**：
- 过强的 Scope Guard、Repair Limit 等机制假设模型容易犯错，当模型规划能力提升后，Task DAG 的细粒度拆分可能反成负担。
- Agent Profile、Expert Agent 设计较固化，不利于快速适配新模型不同的工具调用模式（如 function calling、MCP）。

**哪些模块应保持灵活**：Task DAG 生成器、Executor 调用协议、Hook 规则引擎，均应支持插件化替换。

**哪些能力应可插拔**：模型 Router、Fallback 策略、Prompt 模板、Test Gate 命令集。

**6-12 个月内可能过时的设计**：人工确认 Gate 的过度使用、过于严格的 writeSet 限制（未来模型可能通过测试驱动自我修正更灵活）。

**推荐演进方向**：将规划与分析能力尽快交由更强模型，架构重心从“防护”转向“验证”；引入模型评测反馈环，自动调整约束强度。

---

## 四、开发者上手难度

**评分**：上手难度较高（7/10）。概念数量约 20+（OpenSpec, change, Task DAG, worktree, lockKeys, writeSet, Agent, Hook, Gate, Evidence, Context Pack 等），对普通前端/后端开发者是新语言。

**学习成本判断**：业务开发者若要遵循流程，至少需理解 OpenSpec 结构和 CLI 命令，且部分流程（如编写 change 的 design.md）可能被视为额外文档负担。

**可合并或简化的概念**：Agent Profile 与 Skill 可合并为“Capability”；Evidence 可仅保留 checklist 和 test result，无需过多分类。

**开发者体验优化方案**：提供 VSCode 插件或 IDE 内嵌面板，减少命令行操作；提供交互式向导生成 OpenSpec；自动从代码注释或 PR 描述生成 proposal，降低编写成本。

**最小接入路径**：业务开发者只需在 IDE 中触发一个命令，其余由后台 AI 自动生成 OpenSpec 和 Task DAG 草案，开发者仅需确认和调整，最终执行。

---

## 五、对业务项目的入侵性

**评分**：中等（6/10）。目录新增确实最小集，但 OpenSpec 作为强制需求事实源，与现有 PRD、Wiki、Jira 等如何共存未明确，可能造成“双源”混乱。

**高风险点**：
- `openspec/changes/` 如果要求人工维护，且与代码评审流程脱节，会成为额外工作。
- `.ai-spec/` 中 assets 如果由平台下发，业务项目需要适应其更新节奏。
- 强制 git worktree 可能改变开发者分支习惯，尤其是 feature branch 开发模式。

**推荐低入侵接入**：OpenSpec 可采用 Git 子模块或独立仓库链接；`.ai-spec/` 资产可只拉取不强制提交；Worktree 支持可选的本地直接执行模式（无隔离，仅 L1 用）。

**渐进式迁移**：先在单个模块试点，允许团队保留原有需求文档，OpenSpec 仅作为 AI 执行元数据，不强制人类同步维护全部设计。

---

## 六、系统可靠性与稳定性

**评分**：方案描述了异常路径（失败修复、resume），但离生产级仍有差距（6/10）。

**单点风险**：Worktree 管理器在并发创建/清理时可能损坏 Git 仓库；lockKeys 依赖字符串匹配，可能漏判逻辑冲突。

**链路复杂度**：一次 Run 涉及多个克隆、子进程、patch、merge，失败排查困难。建议每个 Task 记录完整输入输出快照。

**必须补充的可靠性设计**：
- Git 操作全量包装超时与重试，并支持 `git gc` 前检查。
- 提供 `run.log.jsonl` 的结构化日志标准，并配套解析工具。
- 增加对本地模型服务不可用时的降级（如切换到 cache 的指令）。

---

## 七、安全性、权限与治理能力

**评分**：7/10。Scope Guard、Secret Guard、Dangerous File Guard 提供了基础防护，但权限模型较粗。

**不足**：
- 未说明 Agent 调用 LLM 时如何防止泄露敏感代码片段。
- Hook 可被开发者本地绕过，缺乏远程强制校验（V0.1 无平台强控）。
- 缺乏对模型输出内容的合规检查（如是否生成恶意代码）。

**建议补充**：实现可选的 pre-commit hook 扫描输出；在 `.ai-spec-local` 中不缓存明文 Secret；对 Visual 上报脱敏。

---

## 八、可维护性与工程复杂度

**评分**：中（5/10）。模块划分清晰，但整体复杂度高，各模块间耦合紧密（如 Context Pack 依赖 OpenSpec、Task DAG 依赖 Asset Loading），导致修改任一环节可能引发连锁反应。

**技术债风险点**：lockKeys、writeSet 基于 glob 的冲突判断未来可能需要升级为 AST 分析；worktree 管理脚本易因环境不同出错。

**建议**：将各个 Guard 和 Gate 实现为独立可替换的策略函数，降低修改成本；建立全面的契约测试（如 JSON Schema 校验）。

---

## 九、扩展性与复用性

**评分**：较好（8/10）。Skill、Rule、Agent Profile 等设计天然支持复用；三仓架构允许横向扩展；标准协议（JSON Schema）利于多团队协作。

**改进**：Hub 可提前抽象出资产类型注册机制，方便后续新增资产种类；IDE Adapter 模板化已为多 IDE 支持打下基础。

---

## 十、成本与投入产出比

**风险**：V0.1 建设成本高（预计需 3-4 人月以上），对业务团队首次接入有隐性成本（学习 OpenSpec、适应 worktree）。模型 API 调用成本因多次 Agent 交互可能倍增。

**投入产出比判断**：若成功，可显著提升复杂需求交付质量，但早期收益难以覆盖复杂度。建议 **MVP 仅包含 OpenSpec + 单任务 worktree + 基本测试证据**，交付后再逐步增强。

# 七、是否建议通过

**有条件通过**。条件如下：

1. **必须砍掉 V0.1 中不必要的重型机制**：删除 Visual 远程上报、多 Agent 全分层、复杂修复循环；保留单 Agent（或 Executor）模式，worktree 可选。
2. **必须提供全自动 OpenSpec 生成能力**：开发者只需提供一句话需求，系统生成 proposal/design/tasks 草案，人工可编辑但非强制撰写。
3. **必须支持无 worktree 的本地直接执行模式**，降低尝鲜门槛。
4. **必须出具兼容 Windows/macOS/Linux 的完整测试报告**，尤其是 worktree 行为。
5. **重构 CLI 命令**，合并 plan/run/verify 为最小交互步骤。

满足以上条件后，可批准进入 P0 迭代开发。

# 八、修改建议优先级

**P0（最高优先级）**：
1. 精简 Agent 体系，V0.1 只保留 Orchestrator + Executor。
2. Worktree 改为可选特性，支持直接在当前分支执行（非隔离模式）。
3. 自动化 OpenSpec 生成，开发者无需从头手写。
4. 移除 Visual 外部依赖，用本地 `final-report.md` 代替。

**P1（高优先级）**：
5. 增强 context-policy 中的 token 预算硬限制，避免成本失控。
6. 提供 IDE 适配器（Cursor, Claude Code）的最小模板生成。
7. 编写详尽的故障排查指南和常见问题文档。

**P2（中优先级）**：
8. 逐步完善 Test Gate 多级门禁。
9. 引入模型 fallback 配置。
10. 设计轻量级资产同步（从 Hub 拉取本地文件）。

# 九、推荐优化后的架构方向（V0.1 实用版）

**定位**：面向项目级的 AI 执行助手，以“需求 → 受控代码变更 + 测试证据”为核心，不追求完整平台。

**分层**：
- **接入层**：CLI 和 IDE 插件，最小 init 命令。
- **编排层**：单任务计划器（生成 Task 列表，非 full DAG），基于 OpenSpec 视图。
- **能力层**：规则库、Skill 模板、测试命令配置。
- **执行层**：Git 分支管理（仅一个 feature 分支），Executor 顺序执行任务，生成 patch。
- **数据层**：`.ai-spec/` 和 `.ai-spec-local/` 下的配置与证据。
- **观测与运维层**：本地报告、日志。

**核心模块删减**：去除 Task DAG 复杂锁、多 worktree 并行、Merge Agent、Repair Agent 多轮循环；改为人工触发合并与修复。

**开发者路径**：`br init` → 在 IDE 中输入需求 → 系统生成 OpenSpec 草案和任务清单 → 开发者确认/调整 → `br run` → 查看测试报告 → 人工合并至主分支。

**权限与审批**：V0.1 仅依赖 Git 权限和 pre-commit hook。

**可靠性**：单任务失败则停止，记录日志，支持 `br resume`。

**AI 模型适配**：支持配置模型 endpoint 和 api key。

# 十、分阶段落地路线

## 阶段一：MVP 验证阶段（6 周）

- **目标**：在样板项目中完成一次 L2 需求的受控半自动交付。
- **范围**：OpenSpec 草案生成、单分支执行、Scope Guard、单元测试证据。
- **必须建设**：init、plan（生成 proposal, tasks）、run（简单顺序执行）、verify（跑 lint+unit test）、report 生成 markdown。
- **不建议建设**：多 worktree、复杂 Hook、Visual、资产 Hub。
- **验收标准**：一个前端+后端 CRUD 需求，AI 生成代码通过测试且不修改写保护文件；最终报告完整。

## 阶段二：平台化建设阶段（3-4 个月）

- **目标**：支持多项目、资产可复用、初步的 Task DAG 与并行 worktree。
- **核心能力**：资产中心（Manifest, Skill 模板）、工作区隔离、测试门禁分级、轻量 Visual 自建。
- **治理能力**：资产版本锁定、CLI 同步。
- **扩展能力**：插件化 Hook、可定制 Test Gate。

## 阶段三：企业级规模化阶段（6-12 个月）

- **目标**：多团队推广、完整审计和安全策略。
- **范围**：多租户、审批流、模型成本控制、细粒度权限。
- **稳定性**：熔断/降级、分布式 worktree 管理、高可用调度。
- **成本治理**：模型调用统计、预算告警。

## 阶段四：AI 原生演进阶段（12 个月后）

- **目标**：模型自我优化约束、自动化需求澄清、智能修复。
- **范围**：多模型路由与评估、MCP 协议支持、Agent 自主规划与人类协作模式。
- **演进方向**：Guard 逐步由“硬拦截”转为“动态评分”，由强模型接管更多决策。
