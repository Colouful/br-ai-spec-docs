# 企业级 AI 研发控制平面 V0.1 架构评审报告

## 一、评审结论摘要

**总体判断：该方案方向正确但当前设计存在严重的过度工程化问题，不建议按当前方案直接通过。**

方案的核心价值在于：试图将 AI IDE（Cursor/Claude/Codex）从"代码生成工具"升级为"受控的企业研发执行体系"，这在方向上是对的。但当前 V0.1 设计引入了过多概念（Agent、Workflow、Skill、Tool、Hook、Test Gate、Context Pack、OpenSpec、Task DAG、Worktree、Evidence、Patch Bundle 等），形成了一个**概念密集但落地路径模糊**的方案。V0.1 试图一次性解决"规范治理 + 多 Agent 协作 + Git 工作区隔离 + 证据审计 + 运行观测"五大问题，每个问题单独看都有价值，但叠加在一起后，**开发者理解成本极高，业务团队接入意愿将显著降低**。

**关键矛盾**：方案声称"最大限度降低对业务项目的侵入性"，但实际上要求业务项目接受 `openspec/`、`.ai-spec/`、`.ai-spec-local/` 三个新目录、14+ 个 JSON Schema、多 Agent 协作协议、Git worktree 强制隔离——这对一个"标准 L2 需求"（如新增产品配置管理模块）来说，流程重量与需求复杂度严重不匹配。

---

## 二、关键优点

1. **OpenSpec 作为需求事实源的设计思路正确**：将自然语言需求结构化，避免 AI 反复理解同一需求，这是企业级 AI 研发的核心基础设施。
2. **L1/L2/L3 任务分级合理**：按风险等级区分流程重量，避免小需求被大流程拖慢。
3. **Git worktree 隔离执行的想法有创意**：利用 Git 原生机制做并行隔离，比创建多个临时目录更优雅。
4. **渐进式资产披露（Progressive Disclosure）设计正确**：避免一次性塞入全部上下文导致幻觉。
5. **证据落盘（Evidence）理念先进**：在企业级场景中，AI 产出的可审计性比产出速度更重要。
6. **三仓职责分离清晰**：本地控制器、资产治理中心、运行观测中心的边界划分合理。
7. **明确"不做"清单**：V0.1 明确排除了多租户商业化、Agent 市场、全自动上线等高风险能力，体现了克制。

---

## 三、关键问题

1. **概念爆炸，开发者理解成本过高**：V0.1 引入了 20+ 个核心概念，普通业务开发者需要理解 OpenSpec、Task DAG、writeSet、lockKeys、Patch Bundle、Evidence Gate 等才能使用，学习曲线陡峭。
2. **流程重量与需求复杂度不匹配**：一个"新增产品配置管理模块"的 L2 需求，需要经过 OpenSpec → Task DAG → 多 worktree → 多 Agent → Hook → Test Gate → Evidence → Visual 上报等 10+ 个步骤，人工确认节点不足。
3. **多 Agent 并行收益不明确，成本极高**：Task DAG 的并行条件判断（writeSet、lockKeys、dependsOn、风险等级、契约冻结）需要极强的静态分析能力，V0.1 用 glob 匹配 + 字符串 lockKey 远远不够，实际并行率可能极低，但系统复杂度极高。
4. **AI 模型能力假设过于乐观**：方案假设 AI 能够稳定生成准确的 Task DAG、合理分配 writeSet/lockKeys、正确执行 Scope Guard、生成完整 Evidence——这些在当前模型能力下（2026 Q2）远未达到生产级可靠性。
5. **与现有研发流程的集成路径模糊**：方案要求业务项目新增 `.ai-spec/` 入 Git，但 CI/CD、代码评审、Jira/禅道等现有工具链如何对接未明确说明。
6. **Visual 平台价值在 V0.1 阶段存疑**：V0.1 只上报事件，Visual 只展示 Run 列表和 Task DAG，对开发者的日常价值有限，但增加了系统复杂度。
7. **业务项目侵入性被低估**：虽然声称"只新增三个目录"，但 `openspec/` 要求所有 L2/L3 需求写完整 proposal/design/tasks/spec delta/acceptance，这对业务开发者是显著负担。

## 四、分维度详细评审

### 4.1 整体架构合理性

**优点：**
- 三仓职责边界（本地控制器、资产治理、运行观测）划分清晰，符合平台化建设思路。
- Graph-Governed Multi-Agent 的"Graph 管流程、Agent 管判断、Executor 管执行、Hook 管约束"分层思想正确。
- 目录分层（openspec/ 事实源、.ai-spec/ 规范资产、.ai-spec-local/ 运行态）设计合理。

**风险与不合理之处：**
- **模块拆分过细，职责交叉**：`br-ai-spec` 一个 CLI 工具需要承担项目扫描、OpenSpec 管理、Context Pack 构建、Task DAG 生成、Worktree 管理、Executor 调度、Hook 执行、Test Gate、Evidence 生成、Visual 上报等 15+ 个职责，这实际上是一个**小型操作系统**的复杂度，而非一个 CLI 工具。
- **缺乏清晰的接入层设计**：方案没有明确区分"平台开发者"（维护规范资产）和"业务开发者"（使用平台完成需求）的交互界面。
- **编排层与执行层边界模糊**：Task DAG 的生成、调度、执行、合并全部在 `br-ai-spec` 中完成，缺乏独立的编排运行时。
- **数据层设计缺失**：没有明确的数据持久化方案（除了本地 JSON 文件），没有考虑多 Run 的数据管理、查询、归档。

**可优化建议：**
1. 将 `br-ai-spec` 拆分为"核心引擎"（不可变）和"插件扩展"（可变），降低单点复杂度。
2. 明确"编排运行时"独立模块，负责 Task DAG 的调度、状态管理、事件流转。
3. 引入轻量级数据库（SQLite）管理 Run、Task、Evidence 的元数据，而非纯 JSON 文件。
4. 设计"接入层 SDK"和"CLI 层"两个独立入口，SDK 供业务项目集成，CLI 供个人开发者使用。

**推荐目标架构方向：**
```
接入层：CLI / SDK / IDE Plugin
编排层：Task Orchestrator（独立进程/服务）
能力层：OpenSpec Engine / Context Engine / Asset Engine
执行层：Executor Adapter（Cursor/Claude/Codex/MCP）
治理层：Hook Engine / Policy Engine / Test Engine
数据层：SQLite（本地）/ 可选远程存储
观测层：Visual Client（可选上报）
```

### 4.2 目标设计合理性

**目标合理性判断：**

| 目标 | 合理性 | 问题 |
|---|---|---|
| 跑通中台金融系统标准需求完整链路 | ✅ 合理 | 但"完整链路"定义过于宽泛 |
| 生成完整 OpenSpec | ⚠️ 部分合理 | L2 强制完整 OpenSpec 可能过重 |
| 多 worktree 并行执行 | ⚠️ 收益不明 | 实际并行率可能极低 |
| 最多 3 轮自修复 | ✅ 合理 | 但修复范围限定机制未细化 |
| 证据落盘完整率 100% | ✅ 合理 | 但证据格式和存储成本未评估 |
| Visual 上报链路 100% | ⚠️ 存疑 | V0.1 Visual 价值有限 |

**目标优先级建议：**
- **P0（必须保留）**：OpenSpec 结构化、L1/L2/L3 分级、Hook 门禁（Scope Guard + Secret Guard）、Evidence 落盘。
- **P1（建议保留但简化）**：Task DAG 拆解（先做串行，后做并行）、Test Gate 集成。
- **P2（建议降低优先级）**：多 Agent 并行执行、Visual 完整观测、skill-q-platform 完整资产管理。
- **P3（建议暂缓）**：多 worktree 隔离（可用单 worktree + 串行执行替代）、Merge Agent 自动合并、Docs Agent 归档。

**需要补充量化指标：**
- 单个 L2 需求的平均端到端耗时（目标：vs 人工开发节省 X%）
- 业务开发者首次接入的平均学习时间（目标：< 30 分钟）
- Task DAG 生成准确率（目标：> 90%，需人工确认率 < 20%）
- 多 Agent 并行实际加速比（目标：vs 串行执行节省 X%）

### 4.3 面向未来 AI 大模型快速发展的适应性

**适配性评分：6/10**

**分析：**

1. **模型接入与切换**：方案未明确支持多模型路由、模型降级、模型 fallback。当前设计似乎默认使用单一模型（未明确是 GPT-4、Claude 还是其他），缺乏模型抽象层。
2. **Prompt 结构绑定风险**：OpenSpec、Task DAG、Context Pack 等结构如果与特定模型的 Prompt 格式强绑定，未来模型升级后可能需要大规模重构。
3. **Agent/Workflow/Tool Calling 扩展性**：方案提到了 Agent 分层，但未明确是否支持 MCP（Model Context Protocol）等标准协议。2026 年 MCP 已成为行业事实标准 ，方案中未提及 MCP 集成。
4. **模型治理能力**：缺乏模型调用成本控制、调用审计、输出安全、Prompt 版本管理等设计。
5. **"当前模型能力不足导致过度工程化"问题严重**：方案假设 AI 能稳定生成 Task DAG、合理分配 lockKeys、正确执行 Scope Guard——这些在当前模型能力下（即使是 GPT-4o/Claude 3.5）都不可靠。为了弥补模型能力不足，方案引入了大量工程化机制（Task DAG、writeSet、lockKeys、Merge Agent），这些机制本身又增加了系统复杂度。

**当前架构是否容易被未来模型能力替代：**
- **高风险**：如果未来模型（如 GPT-5、Claude 4）具备更强的长上下文理解和代码生成能力，当前大量的"上下文压缩"、"Task DAG 拆解"、"渐进式资产披露"等设计可能变得不必要。
- **中等风险**：Git worktree 隔离、Hook 门禁、Evidence 落盘等机制具有长期价值，不受模型能力直接影响。

**应该保持灵活的模块：**
1. 模型接入层（应支持 OpenAI、Claude、Gemini、Qwen、DeepSeek、本地模型切换）
2. Agent 执行策略（串行/并行应可配置）
3. Context Pack 格式（不应与特定模型绑定）
4. Task DAG 生成方式（应支持 AI 生成、人工编辑、模板继承）

**可能在未来 6-12 个月内过时的设计：**
1. **glob + 字符串 lockKey 的冲突检测**：未来模型可能具备更精确的代码依赖分析能力。
2. **手动 Task DAG 拆解**：未来模型可能具备更强的任务规划能力，自动拆解准确率提升后，人工确认环节可减少。
3. **run.bundle.json 的复杂结构**：如果模型上下文窗口继续扩大，复杂的上下文压缩机制可能变得不必要。

**推荐的 AI 原生架构演进方向：**
1. 引入 **MCP（Model Context Protocol）** 作为工具调用标准 。
2. 设计 **模型抽象层**，支持多模型路由、A/B 测试、成本监控。
3. 将 **AI 能力假设** 显式化：哪些功能依赖 AI，哪些不依赖，AI 失败时的降级策略是什么。
4. 关注 **A2A（Agent-to-Agent）协议** 发展，未来多 Agent 协作应遵循行业标准而非私有协议 。

### 4.4 开发者上手难度

**上手难度评分：8/10（越高越难，10 分为极难）**

**分析：**

1. **概念过多**：Agent、Workflow、Skill、Tool、Plugin、MCP、Runtime、Gateway、Schema、DSL、OpenSpec、Task DAG、writeSet、lockKeys、Patch Bundle、Evidence Gate、Context Pack、Progressive Disclosure——普通业务开发者需要理解 15+ 个新概念。
2. **平台专属规范学习成本高**：需要学习 OpenSpec 格式、Task DAG JSON 结构、Asset 加载等级、Hook 触发时机等。
3. **开发路径不清晰**：文档中描述了"plan → run → verify → report"命令，但没有说明：
   - 如何从零创建一个能力？
   - 如何调试一个失败的 Task？
   - 如何回滚一个错误的 Patch？
   - 如何排查"为什么 Agent 改了不该改的文件"？
4. **缺乏最小接入路径**：方案假设用户已经理解全部概念后才能使用，没有"5 分钟快速上手"路径。

**可以合并或简化的概念：**
| 当前概念 | 建议处理 |
|---|---|
| Skill + Tool + Plugin | 合并为"能力（Capability）" |
| writeSet + readSet + lockKeys | 合并为"任务边界（Task Boundary）" |
| Hook Spec + Test Gate | 合并为"门禁（Gate）" |
| Context Pack + run.bundle.json | 简化为"任务上下文（Task Context）" |
| Evidence + final-report | 合并为"交付物（Deliverable）" |

**推荐的开发者体验优化方案：**
1. **提供"一键初始化"模板**：`br-spec init --template vue-spring-boot` 自动生成样板配置。
2. **提供交互式向导**：`br-spec plan` 使用交互式问答生成 OpenSpec，而非要求用户手写 Markdown。
3. **提供本地调试模式**：`br-spec run --dry-run` 只生成 Task DAG 和预测修改范围，不实际执行。
4. **提供失败诊断工具**：`br-spec diagnose <runId>` 自动分析失败原因并给出修复建议。
5. **提供 IDE 插件**：在 VS Code / Cursor 中直接查看 Task DAG、Evidence、Run 状态。

**推荐的最小接入路径：**
```bash
# Step 1: 初始化（1 分钟）
br-spec init

# Step 2: 描述需求（2 分钟）
br-spec plan "新增产品配置管理模块"

# Step 3: 确认并执行（1 分钟）
br-spec run --confirm  # 先展示预测修改范围，确认后执行

# Step 4: 查看结果（1 分钟）
br-spec report
```

### 4.5 对业务项目的入侵性

**业务入侵性评分：7/10（越高入侵性越强）**

**分析：**

1. **目录侵入**：要求业务项目新增 `openspec/`、`.ai-spec/`、`.ai-spec-local/` 三个顶层目录，`.ai-spec/` 还需入 Git。
2. **规范侵入**：L2/L3 需求强制要求完整 OpenSpec（proposal、design、tasks、spec delta、acceptance），改变了需求文档的编写方式。
3. **Git 工作流侵入**：强制使用 `ai/change/{changeId}` 和 `ai/task/{changeId}/{taskId}` 分支命名规范，可能与企业现有 Git 工作流冲突。
4. **构建侵入**：虽然声称"不修改 package.json / pom.xml"，但 Test Gate 需要执行 `npm run lint`、`mvn test` 等命令，如果项目没有这些命令，需要补充。
5. **CI/CD 侵入**：未明确说明如何与现有 CI/CD 流程集成。如果 `openspec/` 入 Git，CI/CD 是否需要校验 OpenSpec 完整性？

**高入侵风险点：**
1. **`.ai-spec/` 入 Git 导致代码仓库膨胀**：包含 rules、skills、agents、hooks、test-gates、memory 等，可能达到数百 KB 甚至 MB 级。
2. **Git worktree 强制使用**：如果业务团队不熟悉 worktree，或企业 Git 策略限制分支命名，会产生阻力。
3. **OpenSpec 成为需求事实源**：如果企业已有 Jira/禅道/飞书文档等需求管理工具，OpenSpec 与之的关系未明确。

**推荐的低入侵接入方式：**
1. **API 接入**：业务项目通过 REST API 调用 `br-ai-spec` 服务，无需新增目录。
2. **配置化接入**：在现有 `package.json` / `pom.xml` 中增加一个 `ai-spec` 字段，指向外部配置。
3. **Sidecar 模式**：`br-ai-spec` 作为独立进程运行，通过文件系统监听业务项目变更。
4. **可选 SDK 接入**：提供轻量级 SDK，业务项目按需引入。

**推荐的渐进式迁移方案：**
```
Phase 1（零侵入）：br-spec 作为独立工具，手动在业务项目外运行，只生成 OpenSpec 和报告。
Phase 2（轻侵入）：业务项目新增 openspec/ 目录，但不入 Git，作为本地参考。
Phase 3（中度侵入）：openspec/ 入 Git，.ai-spec/ 作为可选配置。
Phase 4（深度侵入）：完整启用 Task DAG、worktree、多 Agent、Hook、Test Gate。
```

**如何设计边界，避免平台逻辑侵入业务核心代码：**
1. **严格分离**：平台只修改 `openspec/` 和 `.ai-spec/` 目录，绝不修改 `src/` 等业务源码目录（除非通过明确的 Patch Bundle 机制）。
2. **契约冻结**：API Contract、DB Schema 等关键契约在 Task 执行前冻结，避免运行时变更。
3. **沙箱执行**：AI 生成的代码先在 worktree 中执行，通过全部测试后才合并到主分支。

### 4.6 系统可靠性与稳定性

**系统可靠性评分：5/10**

**分析：**

1. **错误处理机制**：文档中提到了错误码设计（E_CONFIG_INVALID、E_GIT_DIRTY 等），但缺乏详细的错误恢复策略。
2. **超时、重试、限流、熔断、降级**：未提及。AI 模型调用可能超时或失败，需要明确的重试策略。
3. **任务失败恢复与断点续跑**：提到了 `br-spec resume`，但实现细节不足。如果 Run 在 Task 执行到一半时崩溃，如何恢复？
4. **幂等执行**：未明确说明。如果同一个 Task 被重复执行，是否会重复修改文件？
5. **模型调用失败 fallback**：未提及。如果主模型（如 GPT-4o）失败，是否降级到 Claude 3.5 或本地模型？
6. **工具调用失败补偿**：未提及。如果 Test Gate 中的某个测试命令不存在（如项目没有 `npm run lint`），如何处理？
7. **可观测性**：提到了 Visual 上报，但缺乏日志级别设计、链路追踪、指标监控。
8. **灰度发布与回滚**：未提及。如果 Patch Bundle 合并后发现问题，如何回滚？
9. **权限异常处理**：未提及。如果 Agent 尝试修改超出 writeSet 的文件，是拦截还是告警？

**单点故障风险：**
1. **br-ai-spec CLI 本身**：如果 CLI 崩溃，整个 Run 状态丢失（虽然有 run.bundle.json，但恢复逻辑未验证）。
2. **AI 模型服务**：如果模型 API 不可用，整个系统停摆，缺乏降级方案。
3. **Git worktree**：如果 worktree 创建失败或清理失败，可能导致磁盘空间耗尽或 Git 状态混乱。

**链路复杂度风险：**
- 需求 → OpenSpec → Task DAG → Worktree → Executor → Patch → Merge → Hook → Test → Evidence → Visual，链路长达 10+ 步，任何一步失败都可能导致整个 Run 失败。

**必须补充的可靠性设计：**
1. **状态机设计**：每个 Run、Task、Agent 必须有明确的状态机和状态转换规则。
2. **持久化状态**：Run 状态必须实时持久化到本地数据库，而非仅在内存中。
3. **超时与重试**：每个 AI 调用、每个测试命令、每个 Git 操作都必须有超时和重试机制。
4. **熔断与降级**：模型调用失败时自动降级到备用模型或人工模式。
5. **幂等保证**：同一 Task 重复执行应产生相同结果（或检测到已执行并跳过）。
6. **健康检查**：`br-spec status` 命令检查系统健康状态（Git 状态、磁盘空间、模型 API 可用性等）。

**推荐的可观测性方案：**
1. **结构化日志**：所有操作写入 `run.log.jsonl`，支持按 RunId、TaskId、AgentId 过滤。
2. **链路追踪**：每个 Task 的执行链路（plan → execute → verify → merge）生成 Trace ID。
3. **指标监控**：统计 Run 成功率、Task 平均耗时、测试通过率、自修复成功率、模型调用成本。
4. **告警机制**：Run 失败、测试失败率突增、磁盘空间不足时触发告警。

### 4.7 安全性、权限与治理能力

**安全治理成熟度评分：4/10**

**分析：**

1. **身份认证与权限控制**：未提及。谁可以执行 `br-spec run`？谁可以修改 `.ai-spec/` 中的规则？
2. **角色、资源、动作级别权限**：未提及。Agent 是否有权限访问数据库？Executor Agent 是否有权限修改生产代码？
3. **门禁审批**：提到了 L3 需要"人工确认"，但未说明确认机制（是 CLI 交互？还是 Web 界面？）。
4. **数据隔离与多租户**：V0.1 明确不做多租户，但企业内不同团队的项目如何隔离？
5. **敏感数据脱敏**：提到了 Secret Guard，但实现细节不足。如何识别敏感数据？如何脱敏？
6. **Agent 越权访问**：Scope Guard 可以拦截文件修改，但如何防止 Agent 在代码中植入恶意逻辑（如后门、数据泄露代码）？
7. **Prompt 注入防护**：未提及。如果需求描述中包含恶意 Prompt，如何防护？
8. **输出内容安全**：未提及。AI 生成的代码可能包含安全漏洞（如 SQL 注入、XSS），如何检测？
9. **风险操作二次确认**：未提及。除了 L3 的人工确认，其他高风险操作（如删除文件、修改数据库迁移脚本）是否需要确认？
10. **合规要求**：未提及。金融中台系统通常需要满足等保、PCI-DSS 等合规要求。

**高风险安全问题：**
1. **AI 生成代码的安全性**：AI 可能生成包含安全漏洞的代码（如 SQL 注入、硬编码密钥、不安全的依赖），方案中缺乏自动安全扫描。
2. **Secret 泄露**：虽然 Secret Guard 禁止读取敏感配置，但 AI 可能通过代码分析推断出敏感信息（如数据库连接字符串的格式）。
3. **供应链攻击**：如果 `skill-q-platform` 下发的 Rule/Skill 被篡改，可能导致所有业务项目执行恶意逻辑。

**必须补充的治理能力：**
1. **代码安全扫描**：集成 SAST（静态应用安全测试）工具，如 SonarQube、CodeQL。
2. **依赖安全扫描**：检查 AI 生成的代码是否引入了不安全的依赖。
3. **Secret 扫描**：在 Patch Bundle 合并前扫描是否包含硬编码密钥。
4. **审计日志**：记录谁执行了哪个 Run、修改了哪些文件、调用了哪些模型。
5. **权限模型**：定义"谁可以 plan"、"谁可以 run"、"谁可以修改规则"等权限。

### 4.8 可维护性与工程复杂度

**可维护性评分：4/10**

**分析：**

1. **隐式逻辑过多**：Task DAG 的生成、writeSet/lockKeys 的分配、并行条件的判断都依赖 AI 的"智能"，缺乏可解释性。
2. **配置复杂**：`.ai-spec/` 目录包含 10+ 个配置文件，每个都有 JSON Schema，维护成本高。
3. **测试困难**：方案中提到了单元测试设计，但多 Agent 并行、Git worktree、AI 生成内容的测试难度极高。
4. **本地调试困难**：如果 Task 在 worktree 中失败，开发者需要切换到 worktree 目录手动调试，体验差。
5. **多人协作**：如果多个开发者在同一项目上使用 `br-spec`，如何协调？未提及。
6. **平台团队瓶颈**：`skill-q-platform` 维护规则、技能、Agent Profile，如果只有平台团队能修改，将成为瓶颈。
7. **版本管理**：资产版本（Manifest、Rule、Skill）与业务项目版本如何对齐？未提及。

**容易成为技术债的地方：**
1. **JSON Schema 膨胀**：14 个 Schema 文件，未来每增加一个概念就需要新增 Schema，维护成本高。
2. **glob 匹配规则**：writeSet/lockKeys 使用 glob 匹配，规则复杂后难以维护。
3. **AI 生成内容的不可预测性**：Task DAG、OpenSpec 由 AI 生成，质量不稳定，需要大量人工校验。

**需要简化的设计：**
1. **减少 Schema 数量**：将相关 Schema 合并，如 `run-bundle.schema.json` 和 `task-dag.schema.json` 可以合并。
2. **简化配置**：提供默认配置模板，业务项目只需修改少量字段。
3. **标准化错误处理**：统一错误码和错误恢复策略。

**推荐的工程治理方案：**
1. **Schema 版本管理**：所有 Schema 遵循语义化版本，向后兼容。
2. **配置校验**：`br-spec init` 时校验配置完整性，`br-spec verify` 时校验配置一致性。
3. **自动化测试**：为 CLI 命令、Task DAG 调度、Hook 执行编写自动化测试。
4. **文档自动化**：从 Schema 自动生成 API 文档和配置说明。

### 4.10 成本与投入产出比

**成本风险：高**
**投入产出比：当前不明确，风险较高**

**分析：**

1. **平台研发成本**：三仓改造涉及大量开发工作（CLI、Schema、Worktree、Hook、Test Gate、Evidence、Visual），预计需要 3-5 人团队 3-6 个月。
2. **业务团队接入成本**：每个业务项目需要学习新概念、新增目录、编写 OpenSpec、适配 Test Gate，接入成本高。
3. **模型调用成本**：多 Agent 并行意味着多路模型调用，Token 消耗显著增加。一个 L2 需求可能调用 10+ 次模型，成本可能超过人工开发。
4. **运维成本**：Visual 平台需要部署和维护，Evidence 存储需要磁盘空间管理。
5. **收益不明确**：方案声称"让 AI 按企业流程交付需求"，但未量化收益（如开发效率提升 X%、缺陷率降低 Y%）。

**建议优先建设的能力：**
1. **OpenSpec 结构化 + L1/L2/L3 分级**：这是核心价值，投入产出比最高。
2. **Hook 门禁（Scope Guard + Secret Guard）**：安全底线，必须优先。
3. **Evidence 落盘**：审计刚需，投入相对低。
4. **单 Agent 串行执行**：先跑通单 Agent 链路，再考虑多 Agent 并行。

**建议暂缓建设的能力：**
1. **多 Agent 并行执行**：成本高、收益不明、可靠性差。
2. **Git worktree 隔离**：可用单分支 + 临时目录替代，复杂度低很多。
3. **Visual 完整观测**：V0.1 只做本地 JSON 报告即可。
4. **skill-q-platform 完整资产管理**：V0.1 用本地文件资产即可。

**MVP 建设范围建议：**
```
MVP = OpenSpec 结构化 + 单 Agent 执行 + Scope Guard + Secret Guard + Test Gate（lint + unit test）+ Evidence 落盘 + 本地报告
```

## 九、推荐优化后的架构方向

### 1. 推荐的系统定位

> **企业级 AI 研发规范控制器（V0.1）**：在业务项目本地运行的轻量级规范执行工具，将 AI IDE 的代码生成能力纳入企业规范、测试、审计体系，而非替代现有研发流程。

**关键转变**：从"AI 研发控制平面"降级为"AI 研发规范控制器"，降低定位高度，聚焦核心价值。

### 2. 推荐的架构分层

```
┌─────────────────────────────────────┐
│  接入层：CLI + IDE Plugin + SDK      │  ← 开发者交互入口
├─────────────────────────────────────┤
│  编排层：Task Runner（串行）         │  ← 单 Agent 串行执行
├─────────────────────────────────────┤
│  能力层：OpenSpec Engine + Context   │  ← 需求结构化 + 上下文管理
│         Engine + Asset Engine       │
├─────────────────────────────────────┤
│  执行层：IDE Adapter（Cursor/Claude）│  ← 调用 AI IDE 执行代码生成
├─────────────────────────────────────┤
│  治理层：Hook Engine（Scope/Secret） │  ← 安全底线
│         + Test Engine               │
├─────────────────────────────────────┤
│  数据层：SQLite（本地）              │  ← Run/Task/Evidence 元数据
├─────────────────────────────────────┤
│  观测层：本地 JSON 报告              │  ← evidence-index.json + final-report.md
└─────────────────────────────────────┘
```

### 5. 推荐的接入方式

**渐进式接入（从低到高）：**

```
Level 1（零侵入）：
  br-spec 作为独立工具运行
  手动输入需求，生成 OpenSpec 和报告
  不修改业务项目任何文件

Level 2（轻侵入）：
  业务项目新增 openspec/ 目录（不入 Git）
  使用 br-spec plan 生成 OpenSpec
  人工确认后执行

Level 3（中度侵入）：
  openspec/ 入 Git
  启用 Hook（Scope Guard + Secret Guard）
  启用 Test Gate

Level 4（深度侵入）：
  完整启用所有能力
  接入 skill-q-platform 资产治理
  接入 br-ai-spec-visual 运行观测
```

### 7. 推荐的权限与门禁审批设计

**V0.1 最小权限模型：**

| 角色 | 权限 |
|---|---|
| 开发者 | 执行 L1/L2 需求，查看自己的 Run |
| 技术负责人 | 审批 L3 需求，查看团队 Run |
| 平台管理员 | 修改 Rule/Skill，管理资产版本 |

**门禁设计：**
- **L1**：自动执行，无需审批。
- **L2**：生成 OpenSpec 后自动执行，Test Gate 失败后停止。
- **L3**：生成 OpenSpec 后需技术负责人在 CLI 中确认（`br-spec run --require-approval`），执行后需人工 Code Review。

### 8. 推荐的可靠性设计

1. **状态机**：Run 状态（planned → running → verifying → completed/failed）。
2. **持久化**：Run 状态实时写入 SQLite，支持 `br-spec resume <runId>`。
3. **超时**：AI 调用默认 120s 超时，测试命令默认 300s 超时。
4. **重试**：AI 调用失败重试 2 次，测试命令失败不重试（直接停止）。
5. **幂等**：同一 Task 重复执行时，检测已修改文件并跳过。
6. **健康检查**：`br-spec status` 检查 Git、磁盘、模型 API 状态。

### 9. 推荐的可观测性设计

**V0.1 只做本地可观测性：**

```text
.ai-spec-local/runs/{runId}/
├── run.db              # SQLite 数据库
├── run.log             # 结构化日志
├── evidence-index.json # 证据索引
├── final-report.md     # 最终报告
└── artifacts/          # 附件（测试报告、截图等）
```

**V0.2 再接入 Visual：**
- Visual 只接收元数据（Run ID、状态、耗时），不上传业务源码。

### 10. 推荐的 AI 模型适配策略

1. **模型抽象层**：定义 `ModelProvider` 接口，支持 OpenAI、Claude、Gemini、Qwen、DeepSeek。
2. **默认模型**：V0.1 默认使用 Claude 3.5 Sonnet（代码生成能力强）。
3. **降级策略**：Claude 失败时降级到 GPT-4o，再失败时停止并提示人工介入。
4. **成本控制**：记录每次调用的 Token 消耗，L1 使用轻量模型（如 GPT-4o-mini），L2/L3 使用强模型。
5. **Prompt 版本管理**：将 System Prompt 和 User Prompt 模板化，支持版本切换。

## 十、分阶段落地路线

### 阶段一：MVP 验证阶段（4-6 周）

**目标：** 验证"OpenSpec + 单 Agent 串行执行 + Hook + Test Gate + Evidence"核心链路是否可行。

**范围：**
- 一个真实中台金融系统项目（Vue + Spring Boot）。
- 3 个 L1 轻量修复需求。
- 1 个 L2 标准需求（如新增产品配置管理模块）。

**必须建设能力：**
- `br-spec init/plan/run/verify/report` 命令。
- OpenSpec 生成与验证（L1 简化、L2 完整）。
- 单 Agent 串行任务执行。
- Scope Guard + Secret Guard。
- Test Gate（lint + unit test）。
- Evidence 落盘（evidence-index + final-report）。
- 本地 SQLite 状态管理。

**不建议建设能力：**
- 多 Agent 并行。
- Git worktree 隔离。
- Merge Agent。
- skill-q-platform（用本地文件资产）。
- br-ai-spec-visual（用本地 JSON 报告）。
- 多模型路由（用单一默认模型）。

**验收标准：**
- 能在真实项目中初始化，不破坏原项目结构。
- L2 需求能生成完整 OpenSpec。

- Test Gate 能执行项目测试并阻止失败任务完成。

## 十一、最终评审结论

### 总体评分：4.7/10

### 是否建议通过：**有条件通过**

### 当前最应该优先修改的 5 个问题：

1. **缩小 V0.1 范围至 MVP**：移除多 Agent 并行、worktree 隔离、Merge Agent、Visual，聚焦核心链路。
2. **简化概念体系**：将 20+ 概念合并为 5-8 个，降低开发者理解成本。
3. **补充安全治理**：增加 RBAC、审计日志、代码安全扫描，金融中台系统安全底线不可妥协。
4. **提供最小接入路径**：5 分钟快速上手，一键初始化 + 交互式向导 + dry-run 模式。
5. **增加模型抽象层**：支持多模型切换和降级，避免单点依赖。

### 当前最值得保留的 5 个设计：

1. **OpenSpec 作为需求事实源**：这是企业级 AI 研发的核心基础设施，方向正确。
2. **L1/L2/L3 任务分级**：按风险区分流程重量，避免小需求被大流程拖慢。
3. **渐进式资产披露**：避免一次性塞入全部上下文，降低幻觉风险。
4. **Evidence 证据落盘**：企业级场景中可审计性比速度更重要。
5. **三仓职责分离**：本地控制器、资产治理、运行观测的边界划分合理。

### 面向未来 6 个月、12 个月、24 个月的架构演进建议：

| 时间 | 目标 | 关键动作 |
|---|---|---|
| **6 个月** | 跑通 MVP，验证核心链路 | 完成阶段一（MVP 验证），在 1 个真实项目中验证 OpenSpec + 单 Agent + Hook + Test Gate + Evidence |
| **12 个月** | 平台化建设，支持多项目 | 完成阶段二（平台化），支持 3-5 个项目，接入 skill-q-platform 最小版本 |
| **24 个月** | 企业级规模化，AI 原生演进 | 完成阶段三（规模化）和阶段四（AI 原生），支持 10+ 项目，接入 MCP/A2A 标准，支持多模型生态 |
