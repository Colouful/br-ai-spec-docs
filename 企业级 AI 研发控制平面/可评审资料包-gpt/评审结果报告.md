# 1. 总体吸收结论

我的判断：**这些评审报告整体不是在否定方向，而是在集体提醒：方向成立，但 V0.1 必须降复杂度、补模型抽象、补可靠性与安全底线，并把三仓平台化从“首期必做”改成“分阶段演进”。**

多个模型的核心共识非常明显：

* **产品定位是对的**：不是做 Prompt 仓库，而是把 AI IDE 纳入企业研发流程，让 AI 开发可控、可验证、可审计、可恢复。
* **关键机制值得保留**：OpenSpec、渐进式上下文、Test Gate、Evidence、Hook、Git worktree 隔离、L1/L2/L3 分级都是高价值能力。
* **V0.1 当前范围过大**：三仓同步、完整多 Agent、完整 Visual、完整 Hub、复杂 worktree 并行、复杂 Task DAG 都放进 V0.1，落地风险过高。
* **最严重缺口是模型抽象层**：Claude 报告明确指出没有 AI Model Gateway / Model Registry / Prompt Registry，会导致模型切换、fallback、成本控制、Prompt 版本管理缺失，这是当前最大架构盲区之一。
* **br-ai-spec 过重**：当前 br-ai-spec 承担 CLI、OpenSpec、Context、Task DAG、Scheduler、worktree、Hook、Test Gate、Evidence、Visual 上报等职责，多个模型认为它有“上帝模块”风险。
* **开发者上手难度被低估**：Claude 明确统计当前概念达到 24 个，普通全栈工程师学习成本接近学习一门新框架；DeepSeek、Gemini、Grok、Qwen 也都指出概念过载、流程过重。
* **多 Agent 并行不适合 V0.1 作为默认能力**：多个模型建议先打通单 Agent / 单线串行 / 单 worktree / 证据闭环，再逐步引入多 Agent 和多 worktree 并行。

所以我作为重构负责人会做以下裁决：

## 当前架构最应该保留

| 必须保留                                              | 原因                       |
| ------------------------------------------------- | ------------------------ |
| OpenSpec 作为需求事实源                                  | 能约束 AI 不乱理解需求，是规格驱动开发的基础 |
| L1/L2/L3 分级                                       | 避免所有需求都走重流程              |
| 渐进式上下文加载                                          | 控制上下文膨胀，降低幻觉             |
| Test Gate + Evidence                              | 企业级 AI 交付必须可验证、可审计       |
| Scope Guard / Secret Guard / Dangerous File Guard | 金融中台系统必须内建安全底线           |
| Git worktree 隔离思想                                 | 作为中高风险任务的隔离机制有长期价值       |
| 本地优先执行                                            | 避免平台直接接触业务源码，降低安全和接入风险   |

## 当前架构最应该调整

| 必须调整             | 调整方向                                                        |
| ---------------- | ----------------------------------------------------------- |
| V0.1 范围          | 从“三仓平台化”收敛为“br-ai-spec 本地最小闭环”                              |
| 多 Agent          | V0.1 从 10+ Agent 收敛为 Planner + Executor + Verifier/Reporter |
| Git worktree     | V0.1 默认单 worktree 串行；多 worktree 并行作为 P1/P2 增强               |
| Visual           | V0.1 降级为本地报告 + 可选 mock 上报                                   |
| skill-q-platform | V0.1 降级为本地规范包，Hub 后置                                        |
| Model Gateway    | P0 补上最小 Model Adapter / Prompt Registry / 成本记录              |
| br-ai-spec 内部架构  | 拆分为 Core Engine + Plugin/Adapter，避免上帝模块                     |
| 开发者体验            | 增加 quickstart、dry-run、doctor、abort、clean、交互式 plan           |

## 不应该盲目采纳的建议

| 建议                      | 不盲目采纳原因                                         |
| ----------------------- | ----------------------------------------------- |
| 完全取消 Git worktree       | worktree 是高风险任务隔离的长期价值点，不应删除，只应分阶段启用            |
| OpenSpec 全部移到外部仓库       | 会降低本地需求-代码-证据的一致性；更合理是支持 native / external 两种模式 |
| V0.1 就建设完整 Hub 和 Visual | 会拖垮 MVP，不符合当前阶段                                 |
| V0.1 就做完整 RBAC / 多租户    | 企业级需要，但当前阶段会过度设计                                |
| 让 Merge Agent 自动解决冲突    | 风险过高；合并必须以 Git 确定性操作为主，LLM 只能解释冲突和建议方案          |
| 默认启用多 Agent 并行          | 成本高、调度复杂、收益不确定，V0.1 不默认启用                       |

# 6. 最终推荐的重构方向

## 6.1 系统定位

V0.1 不再定位为完整“企业级 AI 研发控制平面”，而是降级为：

> **企业级 AI 研发规范执行器 V0.1：一个低入侵、本地优先、可审计、可恢复的 AI IDE 约束与交付工具。**

等本地闭环跑通后，再升级为完整 Control Plane。

## 6.2 架构分层

推荐分层：

```text
接入层
  CLI / IDE Adapter / 后续 Webhook

本地控制层
  br-ai-spec Core
  Run State
  Checkpoint
  本地 SQLite / JSON fallback

规格与上下文层
  OpenSpec Engine
  Context Engine
  Asset Pack Loader
  Progressive Disclosure

AI 模型适配层
  Model Adapter
  Prompt Registry
  Cost Logger
  Fallback Policy

执行隔离层
  Execution Runner
  Git Worktree Manager
  Patch Generator
  Deterministic Merge Engine

质量治理层
  Scope Guard
  Secret Guard
  Dangerous File Guard
  Test Gate
  Evidence Gate

观测与审计层
  run.log.jsonl
  evidence-index.json
  final-report.md
  metrics.json
  optional Visual Reporter

平台治理层（V0.2+）
  skill-q-platform
  br-ai-spec-visual
  RBAC / Audit / Asset Versioning
```

## 6.3 核心模块

| 模块                | V0.1 定位 | 说明                                                              |
| ----------------- | ------- | --------------------------------------------------------------- |
| CLI Shell         | 必做      | `init/plan/run/verify/report/resume/abort/clean/doctor/dry-run` |
| Project Scanner   | 必做      | 识别 Vue/Vite/Vuex/SpringBoot/MySQL/Redis/MQ                      |
| OpenSpec Engine   | 必做      | 生成 L2 change，支持 view 压缩                                         |
| Context Engine    | 必做      | 生成最小任务上下文，控制 token                                              |
| Asset Pack Loader | 必做      | 本地读取规则包，不依赖 Hub                                                 |
| Model Adapter     | 必做      | 统一模型调用、记录成本、支持 fallback                                         |
| Task Runner       | 必做      | V0.1 串行执行 Step/Task                                             |
| Worktree Manager  | 必做但简化   | V0.1 单 worktree；多 worktree 后置                                   |
| Guard Engine      | 必做      | Scope/Secret/Dangerous File                                     |
| Test Gate         | 必做      | lint/unit test/API test 最小接入                                    |
| Evidence Writer   | 必做      | evidence-index/final-report                                     |
| Visual Reporter   | 可选      | V0.1 本地 mock 或跳过                                                |
| Hub Client        | 可选      | V0.1 本地资产包替代                                                    |

## 6.4 模块边界

| 模块              | 能做                 | 不能做                   |
| --------------- | ------------------ | --------------------- |
| OpenSpec Engine | 生成/校验需求规格          | 不能直接改业务代码             |
| Model Adapter   | 调用模型、记录成本、fallback | 不能直接写文件               |
| Executor        | 根据 Task 修改代码       | 不能超出 writeSet / scope |
| Merge Engine    | Git 确定性合并          | 不能让 LLM 直接合并冲突        |
| Guard Engine    | 阻断风险操作             | 不能代替测试                |
| Test Gate       | 执行命令并记录结果          | 不能自动忽略失败              |
| Evidence Writer | 生成证据               | 不能篡改测试结果              |
| Visual Reporter | 上报元数据              | 不能上传业务源码              |
| Hub Client      | 同步规范资产             | 不能成为 V0.1 运行强依赖       |

## 6.5 接入方式

V0.1 推荐三个模式：

| 模式          | 场景               | 入侵性                                 |
| ----------- | ---------------- | ----------------------------------- |
| Local-only  | 试点项目，单开发者        | 最低，元数据在 `~/.br-spec`                |
| Repo-native | 团队协作，OpenSpec 入库 | 中，新增 `openspec/` 和 `.ai-spec/`      |
| Hybrid      | 企业项目，资产外部管理      | 中低，OpenSpec external，Evidence local |

默认建议：

```text
V0.1 默认：Repo-native-lite
- openspec/ 可入库
- .ai-spec/ 可入库但最小化
- .ai-spec-local/ 不入库
- worktree 放 ~/.br-spec/worktrees
```

## 6.6 数据流

```text
需求输入
  → OpenSpec Engine 生成 change
  → Context Engine 生成 openspec-view / task-context
  → Model Adapter 调用模型生成计划或 patch
  → Task Runner 执行串行 Task
  → Worktree Manager 隔离修改
  → Guard Engine 检查变更范围和敏感信息
  → Test Gate 执行项目测试
  → Evidence Writer 写入证据
  → Report 生成最终报告
  → Optional Visual Reporter 上报元数据
```

## 6.7 权限与门禁审批

V0.1 必须内置：

* 本地操作审计：谁在什么时候执行了什么命令。
* 高风险文件保护：`.env`、生产配置、CI/CD、lockfile、数据库 migration 历史。
* Secret Guard：读取和输出敏感信息前脱敏或阻断。
* Scope Guard：变更不得超出任务范围。
* Manual Approval Gate：涉及 DB、MQ、Redis、权限、资金、风控默认要求人工确认。
* Model Call Audit：模型调用记录 provider、model、token、耗时、失败原因。

V0.2 再补：

* RBAC。
* 项目空间。
* 资产发布审批。
* 远程审计日志。
* 团队级权限。

## 6.8 可靠性设计

V0.1 必须从开发任务层面补齐：

| 能力   | 具体设计                                                 |
| ---- | ---------------------------------------------------- |
| 超时   | 每个模型调用、命令执行、测试命令有 timeout                            |
| 重试   | 模型调用最多 2 次，测试命令不自动无限重试                               |
| 熔断   | 连续模型失败或测试失败后停止                                       |
| 幂等   | `resume` 重跑不能重复创建 worktree / branch                  |
| 任务恢复 | `run.bundle.json` + `run.log.jsonl` + SQLite 元数据     |
| 失败补偿 | `abort` 清理临时分支、worktree、lock                         |
| 回滚   | 基于 change branch / worktree / patch                  |
| 日志   | JSONL 事件日志                                           |
| 指标   | metrics.json 记录耗时、token、失败率                          |
| 告警   | V0.1 本地输出，V0.2 接 Visual                              |
| 一键清理 | `br-spec abort --run <id>` 和 `br-spec clean --stale` |

## 6.10 AI 模型适配策略

V0.1 最小 Model Adapter：

```ts
interface ModelProvider {
  name: string;
  invoke(request: ModelRequest): Promise<ModelResponse>;
  estimateCost(request: ModelRequest): Promise<CostEstimate>;
}
```

V0.1 必须支持：

* provider 配置。
* model 配置。
* API Key 从环境变量或本地安全配置读取。
* promptTemplate 版本号。
* timeout。
* retry。
* fallback 至人工。
* token / cost 记录。
* 输出 JSON Schema 校验失败时要求模型重试一次。

不做：

* 复杂多模型路由。
* A/B 测试。
* 自动模型评测。
* 企业级模型网关 UI。

# 9. Codex / AI 编程模型执行指令

## 执行目标

将当前 `br-ai-spec` V0.1 从“三仓平台化 + 多 Agent 并行”重构为“本地最小闭环执行器”，优先跑通以下链路：

```text
init → plan → dry-run → run → verify → report
```

本次不得实现完整 Hub、完整 Visual、复杂多 Agent 并行、复杂 RBAC、多租户。

## 修改范围

重点关注以下模块或新增模块：

```text
src/cli/
src/config/
src/project-scanner/
src/openspec/
src/context/
src/model/
src/task-runner/
src/worktree/
src/guards/
src/test-gates/
src/evidence/
src/runtime/
src/reporter/
src/shared/
```

允许新增：

```text
schemas/
assets/default-pack/
templates/prompts/
templates/openspec/
```

## 不允许修改的范围

```text
业务项目 src/ 源码目录结构
业务项目 package.json scripts，除非用户显式同意
业务项目 pom.xml，除非用户显式同意
CI/CD 配置
生产环境配置
.env / application-prod.yml / application-prod.properties
数据库历史 migration 文件
```

不允许：

1. 自动合并冲突。
2. 删除业务文件。
3. 上传业务源码到远程服务。
4. 让 LLM 直接执行 Git merge 决策。
5. 默认启用多 Agent 并行。
6. 默认依赖 skill-q-platform 或 br-ai-spec-visual。

## 具体任务

1. 新增 ModelProvider 接口。
2. 新增 Prompt Template 版本管理。
3. 实现本地 asset-pack 加载。
4. 实现 `br-spec init`。
5. 实现项目扫描。
6. 实现 OpenSpec Lite Builder。
7. 实现 openspec-view。
8. 实现 task-context / run.bundle。
9. 实现串行 Task Plan。
10. 实现 `br-spec dry-run`。
11. 实现单 worktree 创建与清理。
12. 实现 Scope Guard。
13. 实现 Secret Guard。
14. 实现 Dangerous File Guard。
15. 实现 Test Gate 最小版。
16. 实现 Evidence Writer。
17. 实现 `br-spec report`。
18. 实现 `br-spec abort`。
19. 实现 `br-spec doctor`。
20. 完成中台金融系统“产品配置管理模块”样板验证。

## 实现要求

1. 所有命令输出必须为中文。
2. 所有生成文件必须可读、可追踪。
3. 所有 JSON 文件必须 Schema 校验。
4. 所有模型输出必须校验结构。
5. 模型调用失败不能导致文件半写入。
6. Run 状态必须写入 `run.log.jsonl`。
7. 运行态默认写入 `.ai-spec-local/` 或 `~/.br-spec/runs/`。
8. worktree 默认写入 `~/.br-spec/worktrees/{repoHash}/{runId}`。
9. 默认只使用单 worktree。
10. 多 worktree 必须加 `--experimental-parallel` 才能开启。

## 测试要求

必须补充以下测试：

| 测试              | 要求                           |
| --------------- | ---------------------------- |
| init 测试         | 能在空 Git 项目初始化                |
| scanner 测试      | 能识别 Vue/Vite/Vuex/SpringBoot |
| OpenSpec 测试     | 能生成 L2 change                |
| Context 测试      | 不包含未命中文件                     |
| Model 测试        | 模型失败可 fallback 到人工           |
| worktree 测试     | 创建、清理、异常恢复                   |
| Scope Guard 测试  | 越权修改失败                       |
| Secret Guard 测试 | 读取 `.env` 被阻断                |
| Test Gate 测试    | 测试失败不能 report completed      |
| Evidence 测试     | 缺证据不能完成                      |
| abort 测试        | 能清理临时 worktree               |
| report 测试       | final-report 内容完整            |

## 验收标准

1. `br-spec init` 不破坏业务项目。
2. `br-spec plan "新增产品配置管理模块"` 生成 OpenSpec 和任务计划。
3. `br-spec dry-run` 输出预计修改范围、测试命令、风险提示。
4. `br-spec run` 在单 worktree 中执行。
5. 修改文件不得超出计划范围。
6. Secret / Dangerous 文件保护生效。
7. 测试失败时任务不得完成。
8. Evidence 完整生成。
9. `br-spec abort` 可清理异常现场。
10. 不依赖 Hub / Visual 也能跑完。
11. 所有输出为中文。
12. 样板 L2 需求能端到端完成。

## 风险控制

1. 每个命令执行前检查 Git 是否 clean。
2. 每次写文件前创建快照。
3. 每次模型调用设置 timeout。
4. 模型输出结构失败最多重试 1 次。
5. 自修复最多 3 轮。
6. Git merge 冲突必须转人工。
7. 清理命令必须打印待删除清单并要求确认，除非传 `--yes`。
8. 任何高风险文件修改必须阻断。

# 10. 分阶段落地计划

## 阶段一：最小闭环修正

目标：

* 修正 P0 架构问题。
* 保证核心链路可跑通。
* 不做过度平台化。

建设内容：

| 内容                        | 说明                                  |
| ------------------------- | ----------------------------------- |
| br-ai-spec 本地闭环           | init/plan/dry-run/run/verify/report |
| Model Adapter Lite        | provider/model/prompt/cost log      |
| 本地 asset-pack             | 不依赖 Hub                             |
| OpenSpec Lite             | L2 完整但由工具生成                         |
| 单 worktree                | 一个 Run 一个 worktree                  |
| 串行 Task Runner            | 不做复杂并行                              |
| Scope/Secret/Danger Guard | 安全底线                                |
| Test Gate Lite            | lint/unit test/mvn test             |
| Evidence                  | evidence-index/final-report         |
| abort/clean/doctor        | 可靠性和排障                              |

不建设内容：

* 完整 skill-q-platform。
* 完整 br-ai-spec-visual。
* 多 Agent 并行。
* 多 worktree 调度。
* 完整 RBAC。
* 多租户。
* Agent 市场。
* 自动上线。

验收标准：

1. 真实中台金融样板 L2 需求端到端跑通。
2. 不依赖 Hub/Visual。
3. 单 worktree 可创建、执行、清理。
4. 测试失败不能完成。
5. 证据完整生成。
6. 模型调用有成本日志。
7. `abort` 能恢复现场。

---

## 阶段二：企业级能力补齐

目标：

* 补齐权限、门禁、可靠性、可观测性。
* 支持稳定试点使用。

建设内容：

| 内容                      | 说明                                            |
| ----------------------- | --------------------------------------------- |
| skill-q-platform 最小资产治理 | Manifest/Rule/Skill/Prompt/Hook/TestGate CRUD |
| Visual 最小观测             | Run 列表、详情、Evidence                            |
| RBAC Lite               | 项目、资产、发布权限                                    |
| 审计日志                    | 资产变更、Run、模型调用                                 |
| 多模式 OpenSpec            | native/external/managed                       |
| 多模型 fallback            | provider fallback                             |
| SQLite 状态管理             | Run/Task/Evidence 本地数据库                       |
| 可靠性增强                   | resume、stale clean、checkpoint                 |
| 安全增强                    | PII 检测、Prompt 注入防护                            |

不建设内容：

* 大规模多租户商业化。
* Agent 市场。
* 复杂自动审批流。
* 全自动发布。

验收标准：

1. 2-3 个项目可接入。
2. 资产包可从 Hub 下发。
3. Visual 能展示 Run 和 Evidence。
4. RBAC 能限制资产修改和发布。
5. 单次 Run 恢复成功率 ≥ 90%。

---

## 阶段三：平台化与规模化

目标：

* 支持多业务、多团队、多场景接入。
* 提升复用能力和治理能力。

建设内容：

| 内容                | 说明                      |
| ----------------- | ----------------------- |
| 多项目资产分发           | 团队级规范包                  |
| 完整 Visual         | DAG、Agent Trace、Metrics |
| 多 worktree 并行     | experimental → stable   |
| Task DAG 增强       | 并行调度、lockKey、writeSet   |
| Model Gateway     | 路由、配额、成本、审计             |
| Approval Workflow | 高风险任务审批                 |
| CI/CD Adapter     | PR 门禁、流水线上报             |
| 质量指标              | 采纳率、失败率、自修复率、成本         |

不建设内容：

* 不做无边界自治 Agent。
* 不允许模型直接上线发布。
* 不允许平台直接读取生产数据。

验收标准：

1. 支持 5+ 项目。
2. 支持团队规范版本升级。
3. 多 worktree 并行冲突率可控。
4. 模型成本可统计、可限制。
5. Visual 能支撑复盘。

---

## 阶段四：AI 原生演进

目标：

* 支持多模型、Agent、Workflow、Tool、MCP、自动化研发、智能运维等演进。

建设内容：

| 内容               | 说明                |
| ---------------- | ----------------- |
| MCP Tool Adapter | 向标准工具协议对齐         |
| Agent Runtime    | 独立运行时             |
| 中心化 Orchestrator | 云端/团队级调度          |
| 模型评测反馈           | 评估模型生成质量          |
| Prompt A/B       | Prompt 版本实验       |
| 智能规划             | 更强模型自动生成任务计划      |
| 自适应约束            | 根据模型能力调整 guard 强度 |
| 智能运维             | Run 异常诊断、自动建议     |

不建设内容：

* 不替代安全审批。
* 不默认全自动改主干。
* 不忽略企业审计与合规。

验收标准：

1. 支持多模型路由。
2. 支持标准 Tool/MCP 接入。
3. 支持模型能力评估。
4. 支持复杂任务长期运行。
5. 仍保留可回滚、可审计、可人工介入。

# 11. 最终决策摘要

## 11.1 立即采纳

1. 缩小 V0.1 范围为 br-ai-spec 本地最小闭环。
2. 新增 Model Adapter / Prompt Registry Lite / 成本记录。
3. 保留 OpenSpec，但通过工具生成，降低人工成本。
4. 保留 Test Gate / Evidence / Guard。
5. 默认单 worktree 串行执行。
6. Visual / Hub 降级为本地文件或 mock。
7. 禁止 LLM 自动合并冲突。
8. 增加 abort / clean / doctor / dry-run。
9. 增加 metrics.json 和模型调用审计。
10. 降低开发者可见概念数量。

## 11.2 暂缓

1. 多 Agent 并行。
2. 多 worktree DAG 调度。
3. 完整 skill-q-platform。
4. 完整 br-ai-spec-visual。
5. 完整 RBAC / 多租户。
6. MCP 全量集成。
7. Agent 市场。
8. 自动上线。
9. 中心化 Runtime。
10. Prompt A/B 测试。

## 11.3 不采纳

1. V0.1 三仓同时完整建设。
2. LLM 自动处理 Git merge 冲突。
3. 默认所有需求都走重流程。
4. 业务项目必须理解全部 20+ 概念。
5. 默认上传业务源码到平台。
6. 模型调用不做成本和审计。
7. Hub/Visual 不可用时本地任务不可运行。
8. 让多个 Executor 在同一工作区并发改代码。

## 11.4 当前最重要的 5 个重构任务

1. **重切 V0.1 范围**：本地闭环优先，Hub/Visual 后置。
2. **补 Model Adapter**：模型调用统一入口、成本、fallback、Prompt 版本。
3. **重构 br-ai-spec 内部边界**：Core / Runtime / Guard / Evidence / Adapter 分层。
4. **实现单 worktree 串行执行闭环**：先保证安全可运行。
5. **打通 Test Gate + Evidence**：用真实中台样板需求验收。

## 11.5 当前最需要避免的 5 个错误

1. 一开始就做完整三仓平台化。
2. 一开始就做复杂多 Agent 并行。
3. 让 LLM 自动合并冲突。
4. 把所有规则、Skill、Memory 一次性塞给模型。
5. 只做架构文档，不做真实样板端到端验证。

## 11.6 当前架构调整后的最终方向

最终方向不是放弃原方案，而是**降级首期、保留长期架构骨架**：

```text
V0.1：企业级 AI 研发规范执行器
  本地闭环、单 worktree、串行执行、OpenSpec、Guard、Test、Evidence

V0.2：企业级 AI 研发资产治理
  Hub、资产版本、RBAC Lite、Visual 基础观测

V0.3：企业级 AI 研发控制平面
  多项目、多团队、多 worktree、多模型、完整观测

V1.0：AI 原生工程平台
  Model Gateway、Agent Runtime、Workflow、Tool/MCP、成本治理、审计治理
```

我的最终判断：**当前方案“方向通过，原 V0.1 方案不通过”。必须重切 V0.1。先做小而硬的本地闭环，再做平台化。**
