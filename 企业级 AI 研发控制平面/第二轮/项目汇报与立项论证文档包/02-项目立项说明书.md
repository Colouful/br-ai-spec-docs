# 项目立项说明书

## 1. 项目背景

AI 编程工具已经成为研发团队日常工具，但企业研发使用 AI 的主要矛盾已经从“AI 能不能写代码”转向“AI 写代码是否可控、可测、可验收、可复用、可审计、可治理”。

## 2. 行业趋势

| 趋势 | 说明 | 对本项目启发 |
|---|---|---|
| IDE Agent 化 | IDE 从补全升级为可执行任务的 Agent | 平台必须适配不同执行器 |
| Spec-Driven Development 兴起 | OpenSpec 等强调先对齐需求再开发 | Spec 应成为 AI 开发主线 |
| Agent Skills 标准化 | Skills 被多工具支持为可复用能力包 | Skill / Rule 需要资产化 |
| 企业安全要求提升 | 代码、密钥、权限、审计成为推广红线 | 必须有 Harness 与 Policy |
| AI 工具快速迭代 | 各工具能力变化快 | 不能绑定单一 IDE 或模型 |

## 3. 内部现状

1. 开发者根据个人习惯使用 Cursor、Claude Code 或其他工具。
2. Prompt、规则、经验分散在个人聊天记录里。
3. 项目规范难以稳定注入 AI。
4. AI 生成代码后依赖人工 Review 和手工测试。
5. 缺少统一的运行证据和效果度量。
6. 公司难以判断 AI 编程带来的真实效率提升和质量风险。

## 4. 当前问题

| 问题 | 具体表现 | 影响 |
| --- | --- | --- |
| 规范入口不统一 | README、Wiki、聊天记录、个人经验分散 | AI 输出不一致 |
| 工具使用割裂 | Cursor / Claude / Codex 各自维护规则 | 重复配置、难复用 |
| 过程不可控 | AI 可以改代码，但缺少执行边界 | 安全和质量风险 |
| 测试验收弱 | AI 常跳过测试或只口头说明 | 缺陷流入后续阶段 |
| 资产难沉淀 | Prompt、Rule、Skill 不版本化 | 团队经验无法复用 |
| 管理不可见 | 没有运行事件、指标、审计 | 无法量化价值和风险 |

## 5. 建设目标

构建一套企业级 AI 工程开发标准平台，使 AI 开发按照项目规范完成可控、可测、可验收、可追踪、可回滚的工程交付。

## 6. 建设范围

| 阶段 | 建设范围 |
| --- | --- |
| P0 | Cursor + Claude Code 双 IDE 项目级最小闭环：验证单项目规范驱动 AI 开发闭环 |
| P1 | 多项目标准化与 Adapter Protocol：让多项目可复制接入，固化适配协议和资产包标准 |
| P2 | 受控多 Agent 协作：引入专业 Agent，但由 Harness 控制边界 |
| P3 | 企业级治理、权限、审计、灰度、回滚：从团队工具升级为企业可治理平台 |
| P4 | Visual 可观测、质量度量、运行复盘：让 AI 开发过程可视、可度量、可复盘 |
| P5 | Asset Hub、组织级资产复用、资产市场：沉淀组织级 Rule / Skill / Agent / Workflow 资产 |

## 7. 非建设范围

| 非建设范围 | 原因 |
|---|---|
| 替代 Cursor / Claude Code / Codex | 它们是执行器，不是敌人 |
| 自研大模型 | 平台价值在工程治理，不在模型训练 |
| P0 做完整企业平台 | 会过度设计，影响落地 |
| 自动上线发布 | 第一阶段安全风险过高 |
| 无审核资产市场 | 企业级资产必须治理 |

## 8. 核心能力

Project Bootstrap CLI、Spec Center、Harness Runtime、IDE Adapter、Memory Center、Hook Engine、Agent Runtime、Test & Verification Engine、Feedback & Repair Engine、Security & Policy Engine、Local State Manager、Visual Governance、Asset Hub、Enterprise Admin Console。

## 9. 用户角色与场景

| 角色 | 核心诉求 | 平台价值 |
| --- | --- | --- |
| 个人开发者 | 让 AI 更懂项目、更少返工 | 规范、Memory、Command、测试闭环 |
| 团队负责人 | 统一团队 AI 开发方式 | 统一 SOP、规则、验收标准 |
| 架构师 | 控制架构边界和质量 | Spec、Review、Policy、Evidence |
| 测试工程师 | 减少测试遗漏 | Test Plan、Hook、回归记录 |
| 平台团队 | 建设组织级能力 | Adapter、Hub、Visual、治理 |
| 安全/审计 | 控制风险和追溯过程 | 权限、脱敏、审计日志 |

典型使用场景包括：前端需求开发、后端接口开发、组件库能力开发、Bug 修复、测试补齐、代码 Review、规范迁移、新人项目熟悉、多项目规范同步和企业资产治理。

| --- | --- | --- |

## 14. 投入产出分析

短期看，P0 会增加规范整理、CLI 初始化和试点反馈成本；中长期看，平台通过减少重复 Prompt、降低 Review 返工、提升首次测试通过率、沉淀资产和降低安全风险释放收益。

## 15. 风险分析

核心风险包括：过度平台化、工具版本变化、Memory 污染、上手复杂、安全边界不清、AI 幻觉、推广阻力。应对策略详见《11-风险评估与应对方案》。

## 16. 资源需求

| 资源 | P0 最小需求 | 后续扩展 |
| --- | --- | --- |
| 人力 | 负责人、架构师、工具开发、测试、试点开发者 | 后端、DevOps、安全、平台产品 |
| 项目 | 1-2 个真实试点项目 | 多团队、多技术栈项目 |
| 环境 | Cursor、Claude Code、Git、项目测试命令 | Visual、Hub、Admin、私有化部署 |
| 管理支持 | 明确试点范围和验收标准 | 推广制度、资产审核机制 |

## 17. 里程碑计划

M1：完成 P0 初始化、双 IDE 适配、最小闭环。  
M2：完成 P1 多项目接入和 Adapter Protocol。  
M3：完成 P2 受控多 Agent 协作。  
M4：完成 P3 企业治理基础。  
M5：完成 P4 可观测看板。  
M6：完成 P5 资产复用和质量评分。

## 18. 验收标准

| 层面 | 标准 |
|---|---|
| 功能 | P0 可在真实项目完成一次 AI 开发闭环 |
| 质量 | 测试、构建、Review、Evidence 记录完整 |
| 复用 | 规范资产可跨 Cursor / Claude Code 同源生成 |
| 安全 | 运行态和敏感信息不进入 Git |
| 管理 | 可展示阶段成果、风险、指标和投入产出 |
