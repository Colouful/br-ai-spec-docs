# 项目一页纸汇报

## 1. 项目名称

企业级 AI 工程开发标准平台。

## 2. 一句话定位

让 AI 开发按照项目规范完成可控、可测、可验收、可追踪、可回滚的工程交付。

## 3. 项目背景

AI 编程工具已经从代码补全进入 Agent 驱动开发阶段。Cursor、Claude Code、Codex、GitHub Copilot、Devin 等工具正在承担越来越多的代码理解、代码修改、测试运行和 PR 生成任务。但在企业研发场景中，直接使用这些工具仍存在共同问题：项目规范不统一、Prompt 无法复用、过程不可审计、测试验收不稳定、资产无法沉淀、安全边界不清晰。

## 4. 核心痛点

| 痛点 | 表现 | 影响 |
|---|---|---|
| AI 开发不可控 | AI 可直接改代码，但过程不稳定 | 质量、风险、Review 成本上升 |
| Prompt 分散 | 经验留在聊天记录里 | 无法复用、无法传承 |
| 工具割裂 | Cursor、Claude Code、Codex 各自为战 | 规范重复维护，结果不一致 |
| 缺少项目级规范 | AI 不知道项目真实边界 | 代码风格和架构不一致 |
| 缺少验收闭环 | 生成代码后未强制测试 | 缺陷进入后续流程 |
| 缺少资产沉淀 | Rule / Skill / Workflow 不能组织化复用 | 团队经验流失 |
| 缺少企业治理 | 权限、安全、审计、灰度、回滚不足 | 大规模推广风险高 |

## 5. 解决方案

构建一套位于 IDE / Agent 工具之上的平台能力。

```mermaid
flowchart LR
    A[需求] --> B[Spec / Test Plan / DoD]
    B --> C[Rule / Skill / Memory]
    C --> D[Cursor / Claude Code / Codex]
    D --> E[Hook / Test / Review / Repair]
    E --> F[Evidence / Audit / Visual]
    F --> G[资产沉淀]
```

## 6. 核心能力

| 能力 | 说明 |
|---|---|
| Spec-Driven Development | 先明确需求、设计、测试和完成标准，再让 AI 开发 |
| Harness Runtime | 控制上下文、权限、Hook、测试、修复和证据 |
| IDE Adapter | 第一版支持 Cursor + Claude Code，Codex 预留 |
| Memory Center | 管理项目级、团队级、运行级 Memory |
| Hook Engine | 把规范变成可执行门禁 |
| Test / Review / Repair | 形成测试、评审、修复闭环 |
| Evidence / Audit | 形成可追踪、可复盘的交付证据 |
| Asset Hub | 沉淀 Rule / Skill / Agent / Workflow 资产 |

## 7. 对个人 / 团队 / 公司的价值摘要

| 对象 | 价值 |
|---|---|
| 个人开发者 | 少写重复 Prompt，AI 更懂项目，减少返工，测试更完整 |
| 团队开发者 | 统一 AI 开发方式、统一规范入口、统一测试验收标准 |
| 公司 | 降低不可控和安全风险，沉淀研发资产，建立企业级治理能力 |

## 8. 预期收益

| 收益类型 | 预期结果 |
|---|---|
| 效率 | 需求到代码耗时下降，重复性开发提速 |
| 质量 | 首次测试通过率提升，Review 问题数下降 |
| 治理 | Hook、审计、Evidence 覆盖 AI 开发过程 |
| 资产 | 项目经验沉淀为 Rule / Skill / Agent / Workflow |
| 安全 | 减少敏感信息泄露和危险操作风险 |

## 9. 当前阶段目标

P0 先完成 Cursor + Claude Code 双 IDE 项目级最小闭环：单项目初始化、统一规范资产、双 IDE 适配、项目内轻量目录、`~/.ai-spec-auto/` 本地运行态、Spec / Test Plan / DoD、Hook / Test / Review / Repair / Evidence。

## 10. 成本投入摘要

| 投入项 | P0 最小投入 |
|---|---|
| 人力 | 1 名负责人、1 名架构师、1-2 名前端/工具开发、1 名测试、若干试点开发者 |
| 时间 | 3-5 周 |
| 技术成本 | CLI、Adapter、Hook、Local State、基础报告 |
| 推广成本 | 1-2 个试点项目培训和反馈 |

## 11. 上手难度摘要

| 用户类型 | 难度 | 说明 |
|---|---|---|
| 个人开发者 | 低-中 | 执行 init，按生成规则使用 Cursor / Claude Code |
| 团队开发者 | 中 | 需要统一团队规范和试点流程 |
| 企业开发者 | 高 | 涉及权限、审计、安全、资产审核和平台接入 |

## 12. 需要领导支持的事项

1. 允许选定 1-2 个真实项目作为 P0 试点。
2. 指定项目负责人和架构评审人。
3. 允许团队开发者参与反馈。
4. 明确 P0 不追求大而全平台，只验证最小闭环。
5. 支持后续按 P1-P5 分阶段投入。
