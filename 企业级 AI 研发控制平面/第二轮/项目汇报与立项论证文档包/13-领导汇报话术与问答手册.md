# 领导汇报话术与问答手册

## 1. 30 秒电梯陈述

我们要做的不是替代 Cursor、Claude Code 或 Codex，而是在这些工具之上建设一套项目级 AI 工程标准平台。它让 AI 开发先有 Spec、规则、测试和完成标准，再通过 Harness 控制权限、Hook、测试、Review、Repair 和 Evidence，最终实现可控、可测、可验收、可追踪、可回滚的工程交付。P0 先支持公司常用的 Cursor 和 Claude Code，用 3-5 周验证一个真实项目闭环。

## 2. 3 分钟汇报稿

当前 AI 编程工具已经很强，但企业真正的问题不是 AI 会不会写代码，而是 AI 写代码是否可控。现在团队成员各自用 Cursor、Claude Code、Codex，Prompt 分散在聊天里，项目规范不统一，测试验收不稳定，过程不可审计，经验不能沉淀。  
我们计划建设一套 AI 工程标准平台，不替代这些工具，而是把它们作为执行器，统一项目规范、Memory、Rule、Skill、Hook、Manifest 和 Lock。平台通过 Spec-Driven Development 明确需求，通过 Harness Runtime 控制执行边界，通过 Hook / Test / Review / Repair 形成闭环，通过 Evidence / Audit 形成证据。  
第一阶段 P0 只做最小闭环：单项目初始化，Cursor + Claude Code 双 IDE 适配，项目内轻量目录，本地运行态进入 `~/.ai-spec-auto/`，支持 Spec / Test Plan / DoD、Hook、测试、修复和报告。P0 不做完整企业平台、不做资产市场、不做复杂多 Agent。  
预期价值是个人少写重复 Prompt，团队统一 AI 开发方式，公司沉淀规范资产并降低 AI 开发不可控风险。我们建议用 1-2 个真实项目试点，3-5 周形成第一版可验证成果。

## 3. 5 分钟汇报稿

在 3 分钟版本基础上增加竞品和成本说明：Cursor、Claude Code、Codex 是优秀执行器，但它们解决的是具体开发任务执行问题，不解决企业内部跨项目规范治理、资产版本、审计、灰度、回滚问题。我们的平台定位不是重新造 IDE，而是做统一规范底座和治理层。  
P0 人力建议为负责人、架构师、工具开发、测试和试点开发者。P0 成功后再进入 P1 多项目标准化，P2 受控多 Agent，P3 企业治理，P4 可观测，P5 Asset Hub。

## 4. 10 分钟汇报稿

建议按 PPT 大纲展开：背景趋势、当前痛点、解决方案、核心架构、竞品差异、P0-P5 路线、成本投入、上手难度、ROI 指标、风险应对、资源诉求和下一步计划。

## 5. 一句话版本

让 AI 开发按照项目规范完成可控、可测、可验收、可追踪、可回滚的工程交付。

## 6. 面向不同对象的话术

| 对象 | 话术 |
|---|---|
| 研发负责人 | 它能统一团队使用 AI 的方式，减少 Prompt 割裂、测试遗漏和 Review 返工。 |
| 业务负责人 | 它让 AI 加速研发时不牺牲质量和安全，让需求更快更稳定进入交付闭环。 |
| CTO / 技术委员会 | 它是企业 AI Native 工程化的规范底座，核心价值在于协议、门禁、资产治理、审计和可观测。 |
| 开发团队 | 它不是增加流程，而是把你每次重复写的 Prompt、项目规范、测试要求和 Review 经验固化下来。 |

## 7. 高频问题与回答

| 问题 | 建议回答 |
| --- | --- |
| 为什么不直接用 Cursor？ | Cursor 是优秀执行器，但不负责企业级跨 IDE 规范治理、资产版本、审计、灰度、回滚。本项目将 Cursor 纳入执行层，给它统一规范和门禁。 |
| 为什么不直接用 Claude Code？ | Claude Code 的 commands、hooks、subagents 很强，但仍是单工具能力。公司需要跨 Cursor、Claude Code、Codex 的统一项目规范底座。 |
| 为什么不直接用 Codex？ | Codex 适合云端异步工程任务，但 P0 先贴近公司长期使用的 Cursor 和 Claude Code。Codex 预留 Adapter Protocol，后续集成。 |
| 为什么要自研平台？ | 自研边界不是重做 IDE 或模型，而是建设内部规范资产、执行边界、门禁、审计和可观测，这些与公司项目强相关。 |
| 这个项目能给个人带来什么？ | 少写重复 Prompt，AI 更懂项目，减少返工，测试更完整，形成个人可复用资产。 |
| 这个项目能给团队带来什么？ | 统一 AI 开发方式、统一项目规范入口、统一测试验收和 Review 标准，沉淀团队 SOP。 |
| 这个项目能给公司带来什么？ | 降低 AI 开发失控风险，沉淀公司级研发规范资产，建立企业级 AI 工程治理体系。 |
| 这个项目能带来多少效率提升？ | 不应先承诺绝对值。P0 用试点数据衡量需求到代码耗时、采纳率、首次测试通过率、Review 问题数。 |
| 这个项目需要投入多少成本？ | P0 建议 3-5 人、3-5 周。企业级推广需要后端、DevOps、安全、平台运营长期投入。 |
| 个人开发者上手难不难？ | P0 设计为低-中难度，核心动作是安装 CLI、执行 init、在 Cursor / Claude Code 中按命令使用。 |
| 团队推广难不难？ | 中等难度，重点是统一规则和验收标准。先用 1-2 个试点项目降低风险。 |
| 企业级接入难不难？ | 高，需要权限、审计、安全、私有化部署和组织流程，所以放在 P3 之后。 |
| 会不会过度设计？ | 如果一开始做 P3-P5 会过度设计。因此路线明确 P0 只做最小闭环。 |
| 会不会增加开发负担？ | 短期有学习成本，但通过命令化、默认模板和自动报告降低成本，长期减少重复解释、测试遗漏和 Review 返工。 |
| 安全怎么保证？ | 源码默认不上传，运行态放本地目录，敏感信息不进 Git，后续通过 Policy、Audit 和脱敏上报控制。 |
| 如何避免 AI 乱改代码？ | 通过 Harness、allowedFileScopes、pre-edit hook、测试门禁和人工验收限制修改范围。 |
| 如何衡量效果？ | 通过 AI 任务完成率、采纳率、首次测试通过率、Review 问题数、资产复用率、审计覆盖率等指标。 |
| 需要多少人？ | P0 需要负责人、架构师、工具开发、测试和试点开发者。后续企业级阶段需要平台、后端、DevOps、安全角色。 |
| 多久能看到效果？ | P0 3-5 周可完成真实项目闭环，形成第一批指标和反馈。 |
| 后续维护成本高不高？ | 有维护成本，主要是 Rule、Skill、Adapter、文档和培训。通过资产 Owner、版本治理、指标反馈降低成本。 |
| 如果大模型能力升级，这个平台会不会过时？ | 不会。模型越强，越需要项目规范、测试验收、审计和资产治理。这些是稳定工程能力。 |
| 和现有 CI/CD、代码评审、测试体系是什么关系？ | 不替代，只集成。平台调用现有测试命令，生成 Evidence，辅助 Review，接入 CI/CD 门禁。 |
| P0 为什么要先支持 Cursor + Claude Code？ | 因为它们是公司长期使用的主要工具，能最快验证跨 IDE 规范复用。 |
| Codex 为什么后续预留？ | Codex 是重要执行器，但 P0 加入会扩大范围。先定义 Adapter Protocol，后续接入更稳。 |
