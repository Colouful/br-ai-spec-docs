# Spring Cloud 微服务后端工程标准

> 在 Spring Boot 的基础上增加服务发现、配置中心、API 网关、熔断限流、消息、分布式协作等横切能力；**每个**服务仍须遵守 Spring Boot 的分层、安全与可观测基线。

## 适用技术栈

- **语言**：Java 17+，与组织 JDK 基线一致。
- **框架**：Spring Boot 3.x，Spring Cloud 发行版与 **BOM** 对齐；具体组件（如 LoadBalancer、Config、Service Discovery、Resilience4j 等）以项目选型为准并写死于依赖基线。
- **构建**：Gradle 或 Maven，父 POM/平台管理全部依赖版本。
- **运行环境**：Kubernetes/虚拟机/物理机；可观测性（Micrometer、分布式追踪）、配置多环境（中心配置 + 本地仅开发覆盖）。

## 适用项目类型

- **application**：边界清晰、可独立部署的单个业务服务。
- **service**：与业务子域对应的服务，优先拥有独立数据存储与独立发布节奏。
- **microservice**：多服务协作、去中心化数据（在可行时一服务一库）为默认假设；跨服务强一致须显式采用 Saga、TCC、事务消息等方案，不可默认 2PC 跨异构资源。
- **monorepo**：多服务同仓时以模块与目录隔离依赖，CI 按变更增量构建；**禁止** A 服务直接依赖 B 服务实现类，仅通过 API 契约、客户端模块或消息契约集成。

## 项目结构规范

- **Controller、Service、Repository、Entity** 等分层与 `backend-springboot-standard.md` 一致，并补充：
- **client**：供其他服务消费的 Feign/WebClient 接口与 DTO 契约（可独立包或同仓共享模块）。
- **messaging**：入站/出站事件、重试、幂等、消费组与死信配置集中管理。
- **gateway/edge**（若在本仓）：路由、鉴权、限流与下游 API 版本策略的单一配置面。

## Controller 规范

- 与 Spring Boot 一致；**额外**在文档中统一定义对外 API 版本策略（URL/Header/媒体类型任选其一，避免混用无说明）。
- 各服务成功体、错误体与业务错误码体系一致或可映射，便于网关掉点与排障。

## Service 规范

- 用例编排在**本服务**内完成；**禁止**在单个长事务中串联多路同步远程调用；若需读多个下游聚合，须在应用层定义超时、降级、部分失败与可观测信息。

## DTO / VO / Entity 规范

- 对外契约 DTO 与内部持久化/领域模型分离；对外发布契约放在 `client` 或独立契约仓库；不将内部枚举、表结构、实现细节泄漏到公共包（除非有显式版本与向后兼容策略）。

## Repository / Mapper 规范

- 与 Spring Boot 一致；**禁止**跨服务直连对方数据库；禁止**两服务**同时写同一库/同一写路径，除非有强约束的分表/路由/评审结论。

## 异常处理

- 与 Spring Boot 一致；对下游远程错误分类为可重试、不可重试、业务冲突；熔断打开时不得对客户端呈现「半成功半失败」的模糊语义，应返回明确失败或降级数据。

## 参数校验

- 与 Spring Boot 一致；跨服务调用的入参在**本服务入口**一次校验完毕；不依赖对端未文档的隐性约束作为前置条件。

## 日志规范

- 与 Spring Boot 一致；分布式 **trace** 在网关、服务、消息、数据库访问之间可关联；新增日志格式需经可观测/审计一致同意。

## 权限规范

- 与 Spring Boot 一致；网关与业务服务重复鉴权时，**issuer、密钥、角色模型**不互相矛盾；服务间 mTLS/服务账号/Token 轮换有配置清单与轮换策略。

## 事务规范

- 单服务内使用 `@Transactional` 或等价声明；跨服务采用 Saga/补偿/幂等/死信，**不**默认依赖跨异构 2PC。

## 测试规范

- 单元、集成、契约（消费者/提供者或 OpenAPI 校验）并行；用 WireMock、Testcontainers 模拟外部与中间件；网关与关键路由的 E2E 在独立流水线中执行。

## Rule 生成要求

- **约束**：Cloud/Boot BOM 版本矩阵、禁止依赖他方实现 JAR、超时/重试/限流有默认与上界、禁止无契约的同步长调用链。
- **禁止行为**：在业务代码中硬编码对端服务 IP/端口/长期 Token、在消息体中传不可演进且无版本标识的隐式结构。
- **验收标准**：契约在 CI 中可验证、关键 SLO 可测量与可告警。

## Skill 生成要求

- **输入**：服务边界、同步/异步通信方式、配置中心/注册发现类型、SLO 与合规要求。
- **步骤**：定义契约 → 实现本服务 → 配置弹性与可观测 → 多环境联调与故障演练。
- **输出**：无密钥的部署/配置说明、Runbook、真实可用的依赖与版本表（不虚构中间件能力）。
- **异常处理**：写明可回滚/不可回滚、人工介入与消息补偿入口。

## Flow 生成要求

- **阶段**：契约先行 → 实现 → 多环境发布 → 观测/压测/故障注入。
- **门禁**：契约测试、安全扫描、容量与成本基线、回滚/蓝绿/金丝雀方案就绪。
- **状态流转**：发布单与审批、服务版本、配置版本、数据库迁移版本联动。
- **异常出口**：全站降级、只读、熔断、回滚、事件侧补偿与人工对账。

## Manifest 推荐

- **推荐资产组合**：`spring-cloud-bom` 与 `service-mesh-optional`（视平台）、OpenAPI+契约测试、Grafana+Tempo+Prometheus 或等价栈、数据库与配置迁移工具。
- **安装策略**：一次性锁定 BOM 与基础镜像、JDK 版本；不在 Skill 中散播彼此冲突的依赖声明。

## 禁止行为

- 禁止在文档或 Skill 中输出可直接用于生产、未经评审的完整多服务业务实现长代码；不虚构不存在的注册中心/配置/追踪端点与认证方式。
- 禁止在文档中固化、索取生产证书、根密钥、数据库高权限凭据；使用环境变量与密钥管理占位符。
- 禁止默认假定任意外部中间件具备「开箱即用」的强一致与高可用。

## 验收标准

- 多服务联调通过、SLO 与告警可落地、可演练回滚与降级、配置与密钥分符合规。
