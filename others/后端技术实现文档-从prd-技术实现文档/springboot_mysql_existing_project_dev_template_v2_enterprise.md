# 0. AI 开发边界与输出规则

## 0.1 当前任务定位

当前任务是在已有 Spring Boot + MySQL 项目基础上进行增量需求开发。

AI 在输出方案、代码、SQL、接口、测试用例时，必须遵守以下边界：

1. 不允许默认重构现有系统。
2. 不允许默认修改旧接口返回结构。
3. 不允许默认删除旧字段、旧表、旧逻辑。
4. 不允许无理由新增中间件、框架、服务。

# 5. 改造原则与总体策略

## 5.1 改造原则

1. 最小侵入：优先新增扩展点，不轻易修改核心主流程。
2. 兼容优先：旧接口、旧数据、旧调用方必须保持可用。
3. 复用优先：优先复用现有 Service、Mapper、枚举、工具类、错误码。
4. 可灰度：必要时通过配置开关控制新逻辑是否启用。
5. 可回滚：出现问题时能关闭新能力或回退版本。
6. 可测试：每个接口必须有 Apifox 测试用例。
7. 可追踪：关键操作必须有日志、操作人、业务标识。
8. 并发安全：关键写操作必须有幂等、锁、唯一约束或状态机控制。
9. 数据合规：日志、接口、导出均需保护敏感信息。
10. 容量可控：新增表和日志必须评估数据增长与归档。

## 5.2 方案选择

| 方案 | 描述 | 优点 | 缺点 | 是否采用 |
|---|---|---|---|---|
| 方案一 | 修改旧接口扩展能力 | 调用方改动小 | 可能影响旧逻辑 | 是 / 否 |
| 方案二 | 新增接口提供能力 | 兼容性最好 | 需要新增联调 | 是 / 否 |

# 7. 技术方案设计

## 7.1 方案概览

本次需求采用如下技术方案：

1. 在现有模块中新增 / 修改相关接口。
2. 复用现有业务校验逻辑。
3. 新增必要的数据字段 / 数据表。
4. 新增配置开关控制新逻辑灰度。
5. 新增必要的分布式并发控制和幂等控制。
6. 新增 Apifox 单接口用例与场景用例。
7. 通过灰度开关或版本回退保障上线安全。

## 7.2 业务流程设计

### 7.2.1 主流程

```text
客户端 / 前端发起请求
  ↓
Controller 接收请求
  ↓
参数校验
  ↓
权限校验
  ↓
幂等校验 / 分布式锁
  ↓
Service 执行业务规则校验
  ↓
查询 / 写入数据库
  ↓
记录业务日志 / 审计日志
  ↓
释放锁
  ↓
返回响应
```

### 7.2.2 异常流程

| 异常场景 | 触发条件 | 处理方式 | 返回错误码 |
|---|---|---|---|
| 参数缺失 | 必填参数为空 | 返回参数错误 | 400001 |
| 数据不存在 | 根据 ID 查询为空 | 返回业务错误 | 400404 |
| 状态不允许 | 当前数据状态不可操作 | 返回业务错误 | 400409 |
| 无权限 | 当前用户无操作权限 | 返回无权限 | 403001 |
| 获取锁失败 | 资源正在处理中 | 快速失败或返回处理中 | 409001 |
| 外部服务超时 | RPC / HTTP 超时 | 熔断降级或失败补偿 | 503001 |
| 数据库异常 | SQL 执行失败 | 记录日志并返回系统错误 | 500001 |

### 7.2.3 状态流转

| 当前状态 | 操作 | 目标状态 | 说明 |
|---|---|---|---|
| INIT | 提交 | PROCESSING | 进入处理中 |
| PROCESSING | 成功 | SUCCESS | 处理完成 |
| PROCESSING | 失败 | FAILED | 处理失败 |
| FAILED | 重试 | PROCESSING | 重新处理 |

| 锁失败次数 | 分布式锁获取失败 | 持续升高告警 |
| 外部调用失败率 | RPC / HTTP 调用失败 | 超过 x% 告警 |
| 缓存命中率 | Redis / 本地缓存命中 | 低于阈值告警 |

## 11.5 稳定性与安全治理

| 治理项 | 策略设计 | 说明 |
|---|---|---|
| 分布式锁 | Redisson / Redis SETNX | 锁 Key、TTL、失败策略必须明确 |
| 接口限流 | Sentinel / Resilience4j / 网关限流 | 保护下游 DB 与外部系统 |
| 熔断降级 | Sentinel / Resilience4j | 外部服务异常时快速失败 |
| 超时控制 | HTTP / RPC 客户端配置 | 避免线程池被拖垮 |
| 数据脱敏 | VO 与日志统一脱敏 | 符合 PII 合规要求 |
| 日志脱敏 | 日志拦截器 / 工具方法 | 防止日志泄露 |
| 审计日志 | 记录关键写操作 | 操作可追踪 |
| 慢 SQL 防护 | 索引、分页限制、查询条件 | 防止大查询拖垮数据库 |

## 11.6 外部服务容错设计

| 外部服务 | 调用方式 | 超时时间 | 重试策略 | 熔断策略 | 降级策略 |
|---|---|---|---|---|---|
|  | HTTP / RPC | 3000ms | 不重试 / 最多 1 次 | Sentinel / Resilience4j | 返回默认值 / 标记失败 / 进入补偿 |

要求：

1. 禁止无限重试。
2. 禁止在主事务内长时间调用外部系统。
3. 失败要记录可追踪日志。
4. 核心链路必须有降级策略。
5. 可补偿场景必须落失败记录或补偿任务。

# 20. 回滚方案

## 20.1 应用回滚

1. 关闭功能开关。
2. 回退到上一稳定版本。
3. 重启服务。
4. 验证旧接口可用。
5. 执行旧接口回归。

## 20.2 配置回滚

| 配置项 | 回滚值 | 是否动态生效 | 说明 |
|---|---|---|---|
| xxx.feature.enabled | false | 是 / 否 | 关闭新能力 |
| xxx.gray.userIds | 空 | 是 / 否 | 清空灰度用户 |
| xxx.batch.size | 默认值 | 是 / 否 | 恢复默认批量大小 |

## 20.3 数据库回滚

| 数据库变更 | 回滚方式 | 说明 |
|---|---|---|
| 新增字段 | 默认保留 | 避免删字段造成风险 |
| 新增表 | 默认保留 | 不影响旧逻辑 |
| 新增索引 | 如影响性能可删除 | 需 DBA 评估 |
| 迁移数据 | 执行反向脚本 | 必须提前准备 |

## 20.4 回滚验证

| 验证项 | 标准 |
|---|---|
| 服务启动 | 无启动异常 |
| 旧接口 | 可正常访问 |
| 旧数据 | 可正常查询 |
| 新逻辑 | 已关闭或不可访问 |
| 日志 | 无持续异常 |
| Apifox 旧接口回归 | P0 全部通过 |
